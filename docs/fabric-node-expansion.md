# Fabric 节点扩展：补齐其他 MC 版本

> 状态：第 1 阶段实现中（26.2.0-fabric 已加入版本图，当前通过显式 source bridge 复用 26.1.2 Fabric 实现；第 0 步源码上移仍待完成）。
> 涉及的既有决策：[ADR-0007](adr/0007-module-boundaries.md)（三层归属判据——fabric 实现的落位
> 受它约束）、[ADR-0008](adr/0008-guard-discipline.md)（整文件 loader 守卫的纪律与豁免）、
> ADR-0009（发布矩阵）。

## Problem Statement

版本图现在是"NeoForge 三个版本、Fabric 两个过渡节点"的不对称面：`1.21.1` / `26.1.2` / `26.2.0`
是 NeoForge 节点，Fabric 有 `26.1.2-fabric` 和可构建的 `26.2.0-fabric`。后者当前通过
source bridge 复用 26.1.2 实现，尚未独立 runtime smoke；Fabric 用户在 1.21.1 上仍没有
NekoJS 可用，而 NeoForge 侧已有对应制品。

更根本的阻塞是：**Fabric 主线本身还没跑通**。`26.1.2-fabric` 的 jar 能构建，但脚本
运行时没有在 Fabric 上端到端验证过，发布通道因此整体处于注释状态（发版工作流里
Fabric 块未启用）。在这个基线上同时铺开两个新版本，等于把一个未验证的加载器面
复制三份。

还有一个结构性问题要先解决：Fabric 的加载器专属实现（平台适配、事件绑定、mixin、
网络与入口类，约 25 个源文件加资源）目前全部住在 `26.1.2-fabric` 的节点目录里。
节点目录是单节点独享的——**每多一个 Fabric 节点就要复制一整套**。这是版本图扩 Fabric
的唯一真正的架构障碍，也是本 spec 的第一个交付。

## Solution

分两个阶段把 Fabric 面补齐到与 NeoForge 对称，先把实现代码的位置问题解决掉：

**第 0 步（结构前置）**：把 Fabric 加载器专属实现从 `26.1.2-fabric` 节点目录上移到
共享版本树，用整文件 `//? if fabric` 守卫包裹——与现有 `//? if neoforge` 整文件守卫
同一模式、方向相反。此后**所有** Fabric 节点共用单副本（单副本是版本树的立身之本，
复制 25×N 份节点孪生是不可接受的形态）。节点目录只留参数（`gradle.properties`）与
dev run 目录。资源文件（access widener、fabric mixin 配置、mod 描述模板）同样上移，
Fabric 节点约定插件改为从共享树取。

**第 1 阶段（26.2.0-fabric）**：与 `26.1.2-fabric` 同一 MC 时代（Java 25、`>=26` 守卫
区），Fabric API 差异预期为零或极小。当前已新增根级节点 + 参数目录，并通过显式
`deps.fabric_source_node=26.1.2-fabric` source bridge 复用已验证实现；第 0 步源码上移
完成后再移除该 bridge。若勘察发现
26.1↔26.2 的 Fabric API 有差异，差异走共享树内的 `>=26.2` 守卫，不复制文件。这一步
同时是第 0 步的验证：两个 Fabric 节点消费同一份实现，任何"单副本假设不成立"的信号
（守卫交织、求值冲突）都会在这里暴露。

**第 2 阶段（1.21.1-fabric）**：跨代移植，成本结构与当年 Forge 1.20.1 被砍掉时评估的
"第二套代码库"不同——1.21.1 的**版本代差已经被 NeoForge 侧桥接过**（共享树守卫 +
1.21.1 节点孪生），Fabric 要做的是"加载器差 × 已桥接的代差"的交集：Fabric 事件绑定
与 mixin 在 1.21.1 形态下的适配、约 39 个与加载器无关的 1.21.1 孪生对 Fabric 节点的
可用化（复制为节点孪生或上共享树加守卫，按差异量逐文件裁决）、以及 20 个 NeoForge
专属孪生的 Fabric 等价物。**前置条件：26.x Fabric 运行时端到端跑通并开始发布**——
在一个没跑通的基线上叠跨代移植，失败时无法定位是哪一层的问题。

## User Stories

1. 作为 Fabric 玩家，我想在 26.2.0 上装到 NekoJS，这样我不必为了用 NekoJS 留在旧版本。
2. 作为 Fabric 玩家，我想在 1.21.1 上装到 NekoJS，这样与 NeoForge 玩家有相同的版本选择面。
3. 作为服务器主，我想让我的 Fabric 服紧跟 MC 更新，这样我能同时拿到新版本特性与 NekoJS 脚本能力。
4. 作为引擎贡献者，我想让 Fabric 实现只有一份源码，这样修一个 Fabric bug 不需要同步 N 个节点目录。
5. 作为引擎贡献者，我想让"新增一个 Fabric 节点"的成本接近"新增一个参数文件"，这样扩版本面是参数级决策而不是移植级决策。
6. 作为引擎贡献者，我想让 Fabric 实现文件在 IDE 里和 NeoForge 实现一样可跳转（不被埋在节点目录），这样读代码不需要先知道节点机制。
7. 作为引擎贡献者，我想让整文件 `//? if fabric` 守卫享受与 `//? if neoforge` 相同的 lint 待遇，这样守卫纪律对两个方向一视同仁。
8. 作为引擎贡献者，我想在共享树内用 `>=26.2` 这类守卫表达 Fabric 的版本间差异，这样差异留在单副本里而不是裂成孪生。
9. 作为引擎贡献者，我想让 26.2.0-fabric 先落地再谈 1.21.1-fabric，这样跨代移植开工时多节点共享机制已被验证。
10. 作为发版负责人，我想让 Fabric 制品与 NeoForge 制品共享同一发布流程（解开注释即可），这样开闸 Fabric 不需要新机制。
11. 作为发版负责人，我想让 CI 的 build 矩阵自动覆盖新 Fabric 节点，这样漏建某个节点的 jar 在 CI 就红。
12. 作为审阅者，我想让第 0 步（实现上移）的前后产物做等价比对，这样"纯位置变更"有见证而不是口头承诺。
13. 作为脚本作者，我想确认新 Fabric 节点上的脚本 API 与 NeoForge 侧一致，这样同一份脚本跨加载器可移植。
14. 作为脚本作者，我想让 probe 生成的类型声明不因节点扩展而漂移，这样我的编辑器补全不受引擎侧版本图变化影响。
15. 作为新贡献者，我想在版本图文档里看到每个 Fabric 节点的状态（能构建 / 已跑通 / 已发布），这样我不会误把"能构建"当成"能用"。
16. 作为维护者，我想让 1.21.1-fabric 的开工条件写在文档里而不是口头共识，这样时机到了不需要考古决策理由。
17. 作为维护者，我想让 26.1↔26.2 的 Fabric API 差异勘察留下结论，这样后续 26.3 出现时有先例可循。
18. 作为玩家，我想在 CurseForge/Modrinth 上按我的 MC 版本过滤出可用的 Fabric 制品，这样装错版本的挫败不会发生。

## Implementation Decisions

1. **Fabric 实现上移共享树（第 0 步）**：约 25 个加载器专属源文件（平台适配、事件
   绑定、mixin、网络、入口类）从 Fabric 节点目录迁入共享版本树，整文件
   `//? if fabric { … //?}` 包裹；对 NeoForge 节点求值为空文件（与现有
   `//? if neoforge` 守卫的反向用法完全同构）。资源（access widener、mixin 配置、
   mod 描述模板）一并上移；Fabric 节点约定插件里按节点相对路径取这三类资源的逻辑
   改为从共享树取。上移是**纯位置变更**，不改变任何文件内容（守卫包裹行除外）。
2. **节点注册**：版本图新增两个根级节点，均以 Fabric 构建脚本为入口、id 带后缀避免
   与同名 NeoForge 节点撞名（沿用现有 Fabric 节点的命名法）。每个新节点一个参数
   目录：MC 版本、loader 版本、Fabric API 版本、Java 版本、平台常量 `fabric`。
   26.2.0-fabric 的 Java 版本与 26.2.0 NeoForge 节点一致；1.21.1-fabric 与 1.21.1
   一致。
3. **loader 版本钉法**：Fabric loader 本身跨 MC 版本通用，新节点优先沿用现钉版本，
   仅当依赖解析失败时才按版本分别钉。GraalMC 的 Fabric 构建同理（JVM 运行时，与
   MC 版本无关），沿用现有的定向解析版本号。
4. **26.1↔26.2 差异处理**：先做一次 Fabric API 差异勘察并把结论写进本文件。差异为
   零则无动作；差异存在则进共享树守卫（`>=26.2` 一类），**不为版本间差异建节点
   孪生**——孪生保留给"整文件不同"的场合。
5. **1.21.1-fabric 的差异分层**：三个来源分而治之——(a) 纯版本代差：优先复用
   NeoForge 侧已经桥接的表达（共享树既有守卫天然对新节点生效），个别文件按差异量
   裁决"节点孪生 vs 守卫"；(b) 加载器差 × 代差（Fabric 事件/mixin 的 1.21.1 形态）：
   在上移后的共享树 fabric 守卫内加版本分支，差异过大时才落 1.21.1-fabric 节点
   孪生；(c) NeoForge 专属孪生（约 20 个文件）的 Fabric 等价物：逐个评估是否本来
   就有共享树里的中立实现可用。
6. **测试树不启用**：Fabric 节点维持"无测试"的现状（共享测试树整棵在 NeoForge 守卫
   内，Fabric 侧移植是另一个议题），构建脚本里的相应放行保持不变。
7. **CI**：build 矩阵与产物收集模式不变，仅扩节点清单；Fabric 发布块维持注释状态，
   但注释里的制品名清单同步扩（开闸时照抄）。发版 analyze 步骤的 game-versions 输出
   在 Fabric 开闸时才需要动。
8. **guardLint 无需改动**：平台事实源读的是全部节点的参数文件，新节点自动纳入
   （规则 8 的常量集合不变：neoforge / fabric）；整文件 loader 守卫的既有纪律直接
   覆盖上移后的文件。
9. **文档同步**：版本图注释、构建系统文档的节点表与"fabric 侧 = else 分支 + 节点
   文件"的表述、README 的节点清单，随第 0 步一起改。

## Testing Decisions

好的测试只钉外部可观察的行为。本变更的正确性判据分层：第 0 步是"什么都没变"，
新节点是"能构建出内容正确的 jar"，运行时行为靠既有手段（本 spec 不新增运行时验证
机制）。

**不新增测试接缝，复用既有的四个：**

1. **节点 `build`（最高缝）**——新 Fabric 节点的 build 全绿即覆盖编译、资源处理、
   fat jar 装配、loom 重映射。CI 已按节点矩阵跑，扩清单即可。
2. **上移等价比对（第 0 步专属，一次性手工见证）**——上移前后各构建一次既有 Fabric
   节点的 fat jar，内容（类清单 + 资源清单）应当等价；同时全量跑引擎检查
   （guardLint + 引擎模块 check），确认共享树守卫变化没有波及其它节点。这与
   common-api 并入时的"纯移动见证"同一手法。
3. **fat jar 内容断言（既有手工项，建议自动化）**——Fabric jar 不得含 NeoForge 类与
   NeoForge 资源（AT / mods.toml / mixin 配置）。这是唯一值得考虑升格为自动缝的
   项：一个校验任务或 CI 步骤，对每个 Fabric 节点的 jar 做禁止清单检查。升格与否
   留给实施时裁决，不强制。
4. **引擎 golden 全量**——probe golden 与 API manifest 冻结的是引擎表面，节点扩展
   不碰它们；跑一遍全绿即证明"版本图变化对脚本作者无感"。

**运行时冒烟维持手工**：Fabric 节点的 dev run（起服、脚本加载、事件触发）按现状
手工做。1.21.1-fabric 开工的前置条件之一就是 26.x Fabric 的这条手工链路已经走顺。

**先例**：节点级"纯结构变更 + 等价比对"的手法来自 common-api 并入（历史提交
3781a53f 的见证方式）；"新节点 build 全绿 + jar 内容检查"来自 Fabric 26.1.2 落地时
的做法。

## Out of Scope

- **不在本 spec 内让 Fabric 运行时跑通**。脚本运行时在 Fabric 上的端到端验证是
  独立议题（它阻塞的是发布，不是版本图扩展）；本 spec 只承诺"能构建出正确装配的
  jar"。
- **不启用 Fabric 侧测试树**（见实施决策 6）。
- **不动 NeoForge 节点**的任何构建逻辑；NeoForge 侧零感知。
- **不发布任何新制品**。Fabric 发布开闸（含既有 26.1.2-fabric）是运行时验证之后的
  事，本 spec 只保证开闸时"版本面已经齐了"。
- **不做 26.3+ 的预判**；差异勘察的方法留下，结论到时重做。
- **不改脚本 API**：脚本作者侧零变化。

## Further Notes

- **分阶段的裁决点（希望用户确认）**：本 spec 建议的顺序是 第 0 步 → 26.2.0-fabric
  →（等 26.x Fabric 跑通并发布）→ 1.21.1-fabric。如果用户想三步连做，1.21.1-fabric
  的风险是排障时无法区分"Fabric 面的问题"与"1.21.1 面的问题"，因为两个面都没有
  跑通的基线。
- **26.2.0-fabric 的 Fabric API 版本号**：已从 Fabric Maven 元数据定版为 `0.159.0+26.2` 并钉进参数文件；后续升级仍需重新核对元数据。
- **loom 的版本兼容**：节点约定插件经 loom-back-compat 按 MC 版本挑 Loom 变体。
  26.2.0 预期与 26.1.2 同变体；1.21.1 是否有可用变体是第 2 阶段的第一个勘察项——
  如果需要不同变体，插件里按版本分派的逻辑要扩。
- **为什么 Fabric 实现当初落在节点目录**：只有一个 Fabric 节点时，节点目录与整文件
  守卫等价且少一层守卫噪音；第二个节点出现时它才变成债。上移的时机就是现在。
- **与 Forge 1.20.1 教训的关系**：那次砍掉的核心理由是"代差桥接不了"。1.21.1 的代差
  已经被 NeoForge 侧桥接（这是它与 1.20.1 的本质区别），所以 1.21.1-fabric 是"贵但
  可行"，不是"第二套代码库"。判断依据在版本图注释与架构文档里都有记录。
