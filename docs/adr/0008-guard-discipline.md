# 守卫与平台适配纪律

RE1 统计：共享树 250 文件中 190 个含守卫（76%）共 855 行——版本轴（`>=26` 等）占 85%，加载器轴 15%；按包 client 258 > wrapper 193 > api 83；GUI 三屏 55/47/46 行最密。`guardLint` 任务已存在（守卫块配对检查）。M1（ADR-0007）已定"守卫表达不了的下放节点目录"的定性判据，本 ADR 定**定量纪律**：

1. **密度阈值与处置菜单**：文件级硬限 **≤ 20 条守卫**、方法级软告警 ≤ 5 条（落地为"连续守卫段 > 8 行"代理指标，免脆弱的大括号追踪）；超限四选一——① 抽版本 facade ② 拆文件 ③ 下放节点目录 ④ 显式豁免（文件头 `// guard-exempt(20): 理由`——纯 Java 注释，不用 `//?` 前缀以免与 stonecutter 指令语法冲突；guardLint 校验标记并输出豁免清单）。
2. **GUI 高守卫区以 26.2+ 为基准**（用户裁定）：主干 GUI 代码直接按 26.2 API 写，**不为旧版本内联密集守卫**；1.21.1 的 GUI 差异以节点目录适配实现（具体落地归 G1 编排）。这同时把版本守卫的"现代基准"从 `>=26` 收紧到 `>=26.2` 的 GUI 语义。
3. **adapter 触发约定**：守卫内联仍是小差异默认；**同一差异主题在 ≥ 3 个文件重复出现 → 抽版本 facade**（共享树内普通 Java 类 + 少量守卫，不引入新框架/注解/构建机器）；整轴差异（fabric 端口）按 M1 判据下放节点目录。
4. **replacements 边界**：`!mc_ids` / `mc_legacy_api`（现 27 文件）只承载"同一语义的机械改名"（id / 类名 / 方法签名映射）；**逻辑差异必须走守卫**；新增 replacement 条目需在 PR 说明对应版本差异，防止改名表膨胀成隐式守卫场。
5. **guardLint 扩展承载全部检查**：密度阈值、豁免标记校验、wrapper 层零 loader import（ADR-0004 要求）；是否 CI 强制归 G1 裁定。

## Consequences

- GUI 三屏的 148 行守卫在迁移期消失（主干 26.2 化 + 1.21.1 节点适配），全树守卫总量预计显著下降。
- 1.21.1 的 GUI 功能面依赖节点适配的完成度（G1 排期确认；可接受的降级由用户在执行期验收）。
- guardLint 从"配对检查"升级为纪律执行的单一工具入口。
- **P3 落地修订（节点拆分模式确立）**：GUI 三屏之外，4 个豁免文件（mixin / NBT codec / 村民交易 / 配方事件）同样以"节点拆分"处置而非抽 facade——与 M2 裁定方向一致且免除接口设计成本。规范做法：共享树放**纯 26.x 求值版**（整文件守卫 `//? if [neoforge &&] >=26 {`，1 条计数），`versions/1.21.1/src` 放**纯 1.21.1 求值版**。两个实操要点（实测得出）：① 节点目录 src **不走守卫求值**，必须放已求值版本（从该节点 `build/generated/stonecutter` 提取后清掉标记行与 `/*…*///?}` 失活分支）；② 拆分是**行为保持的构造性变换**——节点文件与该节点此前实际编译的求值产物逐字一致，仅源码组织变化。代价是这些文件从此双份维护（改一处须同步两处），只对版本湍流域（GUI / mixin / 平台 codec）使用。守卫块 863 → 626，豁免清单清零。
