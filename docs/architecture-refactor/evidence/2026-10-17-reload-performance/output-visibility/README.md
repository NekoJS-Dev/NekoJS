# 2026-10-18 输出可见性定向诊断

本包用于区分命令处理、RCON 客户端进程和 Gradle 输出转发的时间。**不是正式复验，不改变 `6e5bb8f0` 两组重载 466.4 / 469.4 ms 的 FAIL。** 原 285.3 ms 门槛、采样器、fixtures 和正式失败记录均保留。

## 方法与结果

同一专属性能工作树、NeoForge 26.1.2、JDK 25.0.2、现有六脚本 fixture。只在命令的 root 开始、root 结束、配方结束处插入带单调时钟和 UTC 时间的诊断行；未跳过工作。诊断 RCON 客户端保留原协议和 socket 行为，增加进程内时间点记录；因此其额外导入、观察轮询和时间统计不等于原客户端的精确开销。

预先固定两轮：

1. 十对 `list` / `nekojs reload`，交替先后，每条新建 Python 客户端，间隔 3 s。普通查询的进程退出均值 80.20 ms；重载为 232.88 ms，其中 RCON 命令请求至响应为 159.57 ms、root 120.91 ms、配方 37.29 ms。服务端 UTC 仅毫秒精度，不能把亚毫秒的跨时钟差解释为负耗时或精确调度时延。
2. 十条重载，间隔 3 s，同时观察游戏 `logs/nekojs/server.log`、游戏 `logs/latest.log` 和 Gradle 转发 stdout。每条的同一 marker 在两份游戏日志都先于 Gradle stdout 可见。stdout 比 server.log 晚 **80.04 ms**，范围 **48.33–110.51 ms**。本轮 root / 配方均值为 64.40 / 18.55 ms，客户端退出 158.18 ms；不同会话的 root 数值不构成代码优化的因果对照。

原 fixture marker 在脚本执行中产生，早于配方处理结束；原采样器先等待 RCON 返回，随后每 100 ms 检查转发 stdout。因此原指标包含完整命令和客户端进程耗时，还可能等待转发输出及下一次轮询。这里没有把直接游戏日志或 root 计时替换成正式指标，也没有按诊断数值宣布通过。观察每 5 ms 读取一次各日志，各 sink 依次读取，结果仍有观察与调度误差，不能据此声称某个固定值就是 Gradle 内部独占耗时。
