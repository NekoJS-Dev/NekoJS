# Issue 36: item builder and generated assets research

Read-only source review on 2026-10-12. No source, test, generated, or CI files were changed; no build or test command was run. Existing unrelated workspace edits were preserved.

## Existing behavior

- The startup registry event already owns item definition collection: `RegistryEvents.register` is posted once at the first registry pass, its callback configures a builder, then `RegistryRepository` stores it and `StartupRegistryRuntime.drainFor` hands a validated supplier to the node adapter ([RegistryEvents.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryEvents.java:24), [RegistryEventJS.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryEventJS.java:209), [StartupRegistryRuntime.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/StartupRegistryRuntime.java:107)). Ordinary script reload is not this startup registration lifecycle.
- `ItemBuilder.build()` currently creates item properties and the item; it does not generate a model or texture. The 1.21.1 copy has the same absence. Existing docs tell authors to supply item model/texture files ([26.x ItemBuilder.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/ItemBuilder.java:142), [1.21.1 ItemBuilder.java](D:/mcmodDemo/NekoJS-mult/versions/1.21.1/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/ItemBuilder.java:120), [registering-new-content_us.md](D:/mcmodDemo/NekoJS-mult/wiki/registering-new-content_us.md:57)).
- Nested BlockItems already reuse the same `ItemBuilder`: `BlockBuilder.item` configures it, and the additional ITEM entry uses its `buildProperties()`. Therefore model fields on `ItemBuilder` can cover both standalone items and nested BlockItems; generation must also visit that nested builder, since the co-registration path does not call `ItemBuilder.build()` ([BlockBuilder.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/BlockBuilder.java:126), [BlockBuilder.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/BlockBuilder.java:162), [BlockBuilder.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/BlockBuilder.java:194)).
- The builder contract reflects JavaBean getters/setters into script properties and declarations. Its normalized fingerprint includes all writable properties and recursively fingerprints a nested builder. Simple `parentModel` and `texture` properties therefore fit the existing contract; non-property state added for component methods would need explicit fingerprint coverage. `NekoRegistryDeclarations` also has a hand-authored `ItemBuilder` declaration, alongside the reflected surface/golden ([RegistryBuilderContract.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryBuilderContract.java:182), [NekoRegistryDeclarations.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/NekoRegistryDeclarations.java:46), [RegistryBuilderSurfaceGoldenTest.java](D:/mcmodDemo/NekoJS-mult/src/test/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryBuilderSurfaceGoldenTest.java:17)).
- NeoForge already has the asset writer and resource-pack path. `Assets.itemModel` writes legacy model JSON at `assets/<ns>/models/item/<path>.json`; it supports texture shorthand but does not emit the newer `assets/<ns>/items/<path>.json` client definition. `AssetGeneratorJS` uses `DataGeneratorJS` path validation and atomic writes; the generator replaces a same-path file. The NekoJS disk pack is selected by default at `Pack.Position.TOP` and serves both client resources and server data. The current source does not test user pack reordering or same-path cross-pack precedence ([AssetGeneratorJS.java](D:/mcmodDemo/NekoJS-mult/common/src/main/java/com/tkisor/nekojs/wrapper/AssetGeneratorJS.java:89), [DataGeneratorJS.java](D:/mcmodDemo/NekoJS-mult/common/src/main/java/com/tkisor/nekojs/wrapper/DataGeneratorJS.java:149), [NekoJSPackLoader.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/resource/NekoJSPackLoader.java:24)).
- `DataGenerationBatch` explicitly handles non-Assets data generation. It has contributor tracking and protects pre-existing user-owned files, but that policy does not apply to `Assets` writes ([DataGenerationBatch.java](D:/mcmodDemo/NekoJS-mult/common/src/main/java/com/tkisor/nekojs/wrapper/DataGenerationBatch.java:29), [DataGenerationBatch.java](D:/mcmodDemo/NekoJS-mult/common/src/main/java/com/tkisor/nekojs/wrapper/DataGenerationBatch.java:47)). A generated model sharing a path with a hand-authored file therefore needs a stated collision rule.

## Integration and platform recommendation

Put `parentModel` / `texture` configuration on the existing `ItemBuilder`, and consume it through the existing registry commit/resource-generation owners. Reuse `AssetGeneratorJS`/the existing NekoJS assets root; do not add another registry event or a parallel asset writer. Ensure the contribution path sees both the primary ItemBuilder and `BlockBuilder`'s nested ItemBuilder; generating only inside `ItemBuilder.build()` misses BlockItems and mixes disk writes into item construction. Keep `RegistryEvents.register` and the per-boot `StartupRegistryRuntime` as the declaration owner. A new Plugin Point is unnecessary unless a concrete external plugin contribution needs a distinct collection contract.

The current NeoForge client generation entry point is `onClientResourceReload` -> `postClientGeneration`; in 26.x, `postClientGeneration` runs plugin `generateAssets`, then the script event, then the existing block/spawn-egg defaults ([NekoJSClient.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/client/NekoJSClient.java:83), [NekoJSClient.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/client/NekoJSClient.java:104)). The binding documentation says generated assets take effect on the next resource reload ([NekoJSCorePlugin.java](D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/core/NekoJSCorePlugin.java:290)). The pack is backed by `PathPackResources`, but repository code does not establish whether files written from a reload listener are read during that same in-flight reload; treat first-reload visibility as unverified and cover it with a client resource smoke. For item defaults, use immutable startup metadata and generate missing entries before plugin/script asset hooks so their later explicit writes win. Keep collision ownership local to these auto-generated entries: `DataGeneratorJS` atomically replaces same-path files, and the separate `generateAssets` hook does not use `DataGenerationBatch`'s `generateData` batch/publish path ([DataGeneratorJS.java](D:/mcmodDemo/NekoJS-mult/common/src/main/java/com/tkisor/nekojs/wrapper/DataGeneratorJS.java:175), [PluginGenerationHooks.java](D:/mcmodDemo/NekoJS-mult/common/src/main/java/com/tkisor/nekojs/core/plugin/PluginGenerationHooks.java:53), [PluginGenerationHooks.java](D:/mcmodDemo/NekoJS-mult/common/src/main/java/com/tkisor/nekojs/core/plugin/PluginGenerationHooks.java:74)). A presence-only `getJson` guard cannot distinguish a hand-authored file from a prior auto-generated file on later reloads, so the plan should define how those owned defaults are updated without replacing user assets.

Define same-path precedence for explicit builder settings, script/plugin asset generation, and files already present under `nekojs/assets`; current atomic replace behavior overwrites the last category. The pack is initially enabled at TOP, but the repository has no precedence test. For model format, the supplied KubeJS 26.1.2 reference writes both `models/item/<id>.json` and an `items/<id>.json` wrapper whose `model` is `{type:"minecraft:model", model:"<ns>:item/<id>"}` ([KubeAssetGenerator.java](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/generator/KubeAssetGenerator.java:51), [ItemBuilder.java](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:85)). NekoJS's current `Assets.itemModel` only writes the first file. The old 1.21.1 versus 26.x definition format should be encoded behind the existing version-tree/facade split; 26.1.2 versus 26.2.0 runtime loading and serialization are unverified here and need a client resource smoke.

The existing asset path is NeoForge-only. All three NeoForge nodes have the shared pack loader plus their version-specific `NekoJSPathPackResources`; 1.21.1 retains `generateAssets`/`lang` but intentionally lacks the typed `Assets` binding. Fabric nodes have no pack loader, no `Assets` binding, and no `generateAssets`/`lang` bridge, as pinned by ticket-29 tests ([Ticket29AssetsLangCapabilityTraceTest.java](D:/mcmodDemo/NekoJS-mult/src/test/java/com/tkisor/nekojs/core/Ticket29AssetsLangCapabilityTraceTest.java:35), [Ticket29AssetsAbsentOn1211Test.java](D:/mcmodDemo/NekoJS-mult/versions/1.21.1/src/test/java/com/tkisor/nekojs/core/Ticket29AssetsAbsentOn1211Test.java:17)). A Fabric-only builder file write would not be mounted as client resources. Recommend that the first asset phase state an explicit NeoForge node scope and defer Fabric asset loading, unless the issue explicitly includes a narrow Fabric client-resource pack mount. That does not require implementing general Fabric `generateAssets` parity. Keep asset serialization and writing free of client-only classes: startup registry suppliers run in common mod registration, including dedicated servers.
