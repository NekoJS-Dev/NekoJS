# Issue #36: NekoJS item-registration evidence

Snapshot inspected: `c6455e0477b2f1336a72fbc717d0d5371ae4709f` (`HEAD`). Read-only source and local mapped dependency inspection; no source changes, builds, or tests were made. Existing working-tree changes were left untouched.

## Current surface and registration timing

`RegistryEvents.register(event => { event.item(id, build => { ... }) })` is the generic STARTUP registry API. Item registration is the default `basic` type (`[NekoRegistryPointsPlugin.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/NekoRegistryPointsPlugin.java:56)`). The final argument is already the builder callback, and `RegistryEventJS.addTyped` runs it before adding the builder to `RegistryRepository` (`[RegistryEventJS.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryEventJS.java:209)`). A callback exception therefore prevents that item builder from being published. This guarantee would be lost for new model/texture configuration if its callback writes directly into a shared asset table; keep asset intent inert until callback success and publish it through the asset generation/collector lifecycle.

`RegistryEventAdapter.onRegister` invokes `collectOnce()` and drains only the current registry pass (`[RegistryEventAdapter.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/listener/RegistryEventAdapter.java:56)`). `StartupRegistryRuntime.collectOnce` posts `RegistryEvents.register` at most once; it does not build items there (`[StartupRegistryRuntime.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/StartupRegistryRuntime.java:111)`). During a registry pass `drainFor` records the builder fingerprint and gives a validating supplier to the platform sink (`[StartupRegistryRuntime.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/StartupRegistryRuntime.java:142)`). NeoForge passes that supplier to `RegisterEvent.register` (`[RegistryEventAdapter.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/listener/RegistryEventAdapter.java:116)`); Fabric consumes it from its adapter sink (`[FabricRegistryAdapter.java](/D:/mcmodDemo/NekoJS-mult/src/fabric/java/com/tkisor/nekojs/fabric/FabricRegistryAdapter.java:103)`). Thus `ItemBuilder.build()`/`buildProperties()` run at registration-supplier consumption, not in the script callback. Supplier consumption is loader-specific (Fabric calls `supplier.get()` inline; NeoForge passes it to the registration event), so the exact instantiation instant is not shared. Some component initializers may run later with a `HolderLookup.Provider`.

Current shared 26.x `ItemBuilder` properties are `maxStackSize`, `maxDamage`, `fireResistant`, `rarity`, `glowing`, `burnTime`, `groupTab`, plus the `food(build => ...)` configuration method (`[ItemBuilder.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/ItemBuilder.java:36)`). `buildProperties()` sets item id, stack/durability, fire resistance, rarity, and food; it directly writes the consumable component for food (`[ItemBuilder.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/ItemBuilder.java:182)`). It exposes no general `component(...)`, `components` property, `jukeboxPlayable`, `trimMaterial`, `parentModel`, or `texture` member. The 1.21.1 pair has the same existing configuration fields and food builder (`[ItemBuilder.java](/D:/mcmodDemo/NekoJS-mult/versions/1.21.1/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/ItemBuilder.java:27)`) and likewise no such members; its `Item.Properties` construction differs (`[ItemBuilder.java](/D:/mcmodDemo/NekoJS-mult/versions/1.21.1/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/ItemBuilder.java:121)`). `BlockBuilder` owns a nested `ItemBuilder` and reuses its `buildProperties()` for the co-registered `BlockItem` (`[BlockBuilder.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/BlockBuilder.java:202)`), so additions to that method affect both item creation paths.

The separate `Item` binding is a stack factory/query (`Item.of`, `Item.id`, `Item.idOf`), not a registration builder (`[ItemJS.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/bindings/static_access/ItemJS.java:13)`). On the shared 26.x stack-conversion path, `{ item, count, components }` calls `DataComponentsAdapter.toPatch` and applies the resulting patch to a copied `ItemStack` (`[ItemStackAdapter.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/js/type_adapter/ItemStackAdapter.java:136)`). The adapter converts the JS object to JSON and parses `DataComponentPatch.CODEC` with plain `JsonOps.INSTANCE`, raising `ValueConversionException` on parse failure (`[DataComponentsAdapter.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/js/type_adapter/DataComponentsAdapter.java:22)`). That is a reusable format/error precedent, not proof that arbitrary registry-backed component codecs can resolve during STARTUP. `ItemEvents.modification` is a different live-modification path and is out of scope for this registration plan.

## Version findings

The checked-in version graph is 1.21.1, 26.1.2, and 26.2.0; both 26 versions also have Fabric nodes sharing the 26.x `src/` tree (`[settings.gradle.kts](/D:/mcmodDemo/NekoJS-mult/settings.gradle.kts:38)`). I inspected the local mapped `Item.Properties` classes read-only with `javap` from `versions/1.21.1/build/moddev/artifacts/neoforge-21.1.227-merged.jar` and `.gradle/loom-cache/minecraftMaven/net/minecraft/minecraft-merged-13d0e37412/{26.1.2,26.2}/...jar`.

- All three checked versions expose `Item.Properties.jukeboxPlayable(ResourceKey<JukeboxSong>)`. In 1.21.1 the method immediately stores a `JukeboxPlayable` carrying an `EitherHolder(ResourceKey)`; in 26.x it registers a delayed component initializer that resolves the key through `HolderLookup.Provider`. Both are key-based paths that avoid eagerly looking up the dynamic song registry from the STARTUP callback. A Neko `jukeboxPlayable` Bean property can accept a string id, validate it as a resource key, and call the native method when building properties.
- `Item.Properties.trimMaterial(ResourceKey<...>)` exists in the inspected 26.1.2 and 26.2 classes and writes delayed `DataComponents.PROVIDES_TRIM_MATERIAL`. It is absent from 1.21.1 `Item.Properties`; that version has `DataComponents.TRIM` (`ArmorTrim`, a pattern-plus-material value) instead. This is a real semantic/version split, not an accessor rename. Either expose `trimMaterial` only on the 26.x builder/declarations and document availability, or make a compatibility API a separate feasibility decision; do not imply 1.21.1 has the modern native behavior.
- Generic components need a focused spike before promising uniform STARTUP decoding. `DataComponentsAdapter` uses `JsonOps`, which supplies no dynamic registry lookup; the native jukebox path proves that a resource-key property can be deferred, not that the generic JSON component codec can resolve such a key. Reuse the JSON conversion, `DataComponentPatch.CODEC`, and `ValueConversionException` shape for codec-supported values, but establish a registry-aware/deferred decode path (and rejection behavior) for registry-backed values. Avoid eager `BuiltInRegistries` holder lookup in the callback.

## Suggested Script API and state contract

Preserve the existing callback-last shape:

```js
event.item('mymod:disc', build => {
  build.component('minecraft:enchantment_glint_override', true);
  build.components = { 'minecraft:custom_data': { source: 'pack' } };
  build.jukeboxPlayable = 'mymod:disc_song';
  build.trimMaterial = 'mymod:trim_material'; // 26.x only unless compatibility is proven
});
```

Expose component ids as strings instead of Minecraft Java generic tokens. Add `component(id, value)` as a parameterized builder method and `components` as a writable Bean property for bulk input; both must update the same canonical component state. The Neko `ItemBuilder` currently exposes no typed `component(DataComponentType<T>, T)` method, even though native `Item.Properties` has one; do not expose Java generic tokens to scripts. Give `jukeboxPlayable` and (26.x) `trimMaterial` readable/writable Bean properties, since each is one named scalar configuration. Keep the public builder API derived from its Java accessors/methods rather than adding a second hand-maintained member list.

One important contract gap: `RegistryBuilderContract` discovers accessors/methods for `BuilderSurface`, but `normalizedPropertyReadings` fingerprints only `WRITABLE_PROPERTY` values (`[RegistryBuilderContract.java](/D:/mcmodDemo/NekoJS-mult/src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryBuilderContract.java:200)`). A method that mutates hidden component state alone can be callable while leaving the registration receipt unchanged. Use a canonical getter/setter-backed component state, or explicitly extend the fingerprint contract; do not leave the generic payload behind method-only mutable state. A stable, sorted/canonical representation is needed so equivalent component declarations yield equal fingerprints.

Recommended duplicate policy: basic native builder properties run first; explicit generic component entries overlay them last. Repeated `component(id, value)` calls replace that id (last write wins); assigning `components = object` replaces the whole generic map; later `component(id, value)` calls update individual entries. Reject a generic entry that collides with a named deferred property (`jukeboxPlayable` or `trimMaterial`) unless both are represented in one canonical typed entry, since relying on the internal merge order of immediate and delayed `Item.Properties` initializers is not established by the current Neko code. Validate full component ids and values at the script boundary with a component-specific conversion error. For components whose codec needs a dynamic registry, preserve the resource key and resolve through the initializer provider at the correct later phase; reject failures rather than silently dropping them.

Model parent/texture values belong to client resource assets, not `Item.Properties`. The item builder has no current model or texture fields. Keep this in the asset workstream: use the existing asset binding/generation route, and ensure a failed item callback cannot publish a partially registered item asset. No direct asset mutation from an item setter should occur before `addTyped` succeeds.
