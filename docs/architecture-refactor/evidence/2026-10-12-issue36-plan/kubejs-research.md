## Builder API and component decoding

- `ItemBuilder` extends `ModelledBuilderBase<Item>`. It exposes a generic singular `.component(DataComponentType<T>, T)` method that stores its key and value in a transient map; this source has no `.components(...)` mutator and no `.trimMaterial(...)` convenience method. See [ItemBuilder.java:36](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:36) and [ItemBuilder.java:126](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:126).
- During `createItemProperties()`, KubeJS resolves each stored key through `DataComponentWrapper.wrapType`, then passes the stored value straight to `Item.Properties.component`. This path does not decode JSON or run the generic value wrapper. For the builder method, callers need a value compatible with that component’s Java type; a JSON-shaped object is not automatically converted by this path. See [ItemBuilder.java:248](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:248).
- The separate `DataComponentWrapper` shows KubeJS’s richer decode path. It accepts a `DataComponentMap`, patch, builder callback, JSON object, NBT compound, map, or component-syntax string. JSON objects use `DataComponentMap.CODEC`; map entries go through `tryWrapComponent`, which first attempts registered type conversion and then parses with the component codec. Unknown component IDs fail registry lookup; invalid values return codec errors. See [DataComponentWrapper.java:308](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/component/DataComponentWrapper.java:308), [DataComponentWrapper.java:391](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/component/DataComponentWrapper.java:391), and [DataComponentWrapper.java:100](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/component/DataComponentWrapper.java:100). The separate patch path treats a null map entry as removal, while a null value in a full map is skipped.
- KubeJS already has `.jukeboxPlayable(ResourceKey<JukeboxSong>)`; it stores the song key and later calls `Item.Properties.jukeboxPlayable`. See [ItemBuilder.java:238](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:238) and [ItemBuilder.java:297](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:297). No `trimMaterial` method exists in this snapshot; `DataComponents.TRIM` is only referenced in the component wrapper’s visual-difference set ([DataComponentWrapper.java:86](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/component/DataComponentWrapper.java:86)). Treat trim support as a target-version-specific typed component contract rather than something this reference implements.

**Implication for NekoJS:** keep component decoding at a version-aware boundary. A small API can preserve direct typed values while adding a batch `components(map)` form that resolves component IDs and converts each value through the target component codec/type adapter before registration. Do not route a raw JSON object to `Item.Properties.component` and assume it will decode. Keep Minecraft component classes and codecs out of NekoJS `common`. KubeJS’s `jukeboxPlayable` name and `ResourceKey<JukeboxSong>` parameter are useful precedent; the issue’s spelling `jukeplayable` should be normalized deliberately in the proposed public API. KubeJS offers no precedent for `trimMaterial`, so settle its exact type and resulting component against each NekoJS node’s Minecraft API.

## Model and texture generation

- [ModelledBuilderBase.java:14](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/registry/ModelledBuilderBase.java:14) supplies `.texture(String)` for the base texture, keyed `.texture(String[], String)`, `.textures(Map)`, `.parentModel(Identifier)`, and `.modelGenerator(...)` (see also [ModelledBuilderBase.java:28](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/registry/ModelledBuilderBase.java:28) and [ModelledBuilderBase.java:49](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/registry/ModelledBuilderBase.java:49)).
- `ItemBuilder` initializes its base texture as the item ID under `item/<path>`. Its default generator uses `minecraft:item/generated` unless a parent is supplied; with no keyed texture map it writes that texture as `layer0`, otherwise it writes the provided texture map. Thus layered generated items use entries such as `layer0`, `layer1` and a compatible parent model; there is no separate layered-item helper. A custom model generator replaces that default parent/texture branch. See [ItemBuilder.java:54](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:54) and [ItemBuilder.java:90](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/item/ItemBuilder.java:90).
- In this 26.1.2 source, `KubeAssetGenerator.itemModel` emits both a model JSON at the `models/item/<path>` resource ID and an item definition at `items/<path>`. The definition JSON wraps a `minecraft:model` reference to the model ID and optionally carries `tints`. [ID.java:25](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/util/ID.java:25) defines these resource paths; [GeneratedData.java:43](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/script/data/GeneratedData.java:43) appends `.json`. See [KubeAssetGenerator.java:51](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/generator/KubeAssetGenerator.java:51) and [KubeAssetGenerator.java:57](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/generator/KubeAssetGenerator.java:57). The referenced model JSON still contains the `parent`, `textures`, `elements`, and `overrides` fields emitted by [ModelGenerator.java:176](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/client/ModelGenerator.java:176).
- For the cross-version plan, preserve the 1.21.1 legacy output as a direct `assets/<namespace>/models/item/<path>.json` item model. The 26.1.2 reference additionally requires `assets/<namespace>/items/<path>.json` to point at that model. This KubeJS directory contains only the 26.1.2 source, so the 1.21.1 half is a Minecraft-format boundary to verify against NekoJS’s local 1.21.1 node sources, not a behavior demonstrated by this KubeJS checkout. Implement output selection in the version asset facade; do not emit the 26.1 item definition into a 1.21.1 node.

## Generation lifecycle and precedence

KubeJS generates assets into in-memory `VirtualAssetPack` instances. During client resource-pack loading, [MinecraftClientMixin.java:56](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/core/mixin/MinecraftClientMixin.java:56) calls `ClientAssetPacks.inject` around `PackRepository.openAllSelected()`. The injector scans `kubejs/assets` for zip packs and its directory pack, inserts `BEFORE_MODS`, internal builder-generated assets, `AFTER_MODS`, the file packs, and `LAST` in that order, then resets and regenerates the internal and script packs. See [ClientAssetPacks.java:50](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/client/ClientAssetPacks.java:50), [ClientAssetPacks.java:67](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/client/ClientAssetPacks.java:67), and [ClientAssetPacks.java:150](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/client/ClientAssetPacks.java:150). Script asset stages are `AFTER_MODS`, `BEFORE_MODS`, and `LAST` ([GeneratedDataStage.java:10](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/script/data/GeneratedDataStage.java:10)). The ordered pack list is part of KubeJS’s resource-pack integration; NekoJS should keep its own resource and generation lifecycle, using only the generated resource shapes and builder behavior as reference.

[VirtualResourcePack.java:28](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/script/data/VirtualResourcePack.java:28) stores resources by identifier and serves them from an in-memory map; its export method is a distinct explicit path ([VirtualResourcePack.java:145](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/script/data/VirtualResourcePack.java:145)). The file source’s `findBeforeModsIndex` and `findAfterModsIndex` anchor insertion around vanilla and file packs ([KubeFileResourcePack.java:85](D:/kubejs-2601/src/main/java/dev/latvian/mods/kubejs/script/data/KubeFileResourcePack.java:85)). Do not copy this injection machinery, KubeJS’s plugin hooks, script lifecycle, or caches into NekoJS.

## Minimal behaviors to carry into the plan

1. Support typed singular component assignment and a batch component map only if issue #36 requires it; resolve namespaced IDs per target registry and validate/decode before creating the item.
2. Add the requested jukebox builder method with the target node’s registered song key/value type. Treat the issue spelling as a naming decision and document the chosen script-facing spelling.
3. Define trim material behavior from each target version’s actual component/API; this KubeJS snapshot supplies no helper contract.
4. Reuse `parentModel`, base texture, and keyed texture-map semantics. For generated layered items, default the parent to `minecraft:item/generated` and map `layer0..layerN`; preserve a user-selected parent.
5. Route model serialization through the existing version asset facade: 1.21.1 direct model file, 26.1 item definition plus model file. Let the owning resource lifecycle decide when and where those files are served.
