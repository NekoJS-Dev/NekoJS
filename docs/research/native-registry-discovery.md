# 能否自动发现模组已建立的原生注册表？

**可以发现已安装的表键，不等于可以写入，更不等于能自动创建表内对象。** 配方能回退到 JSON，是因为已有原生 serializer 提供解码契约；裸 `Registry<T>` 没有等价契约。这里的“原生表”指加载器已经安装的静态表，不是脚本新建表，也不是数据包注册表。

## 配方究竟发现了什么

- **NeoForge 和 Fabric 都能读取原生条目 ID，但要分清两个表。** 两侧目录都从 `RegistryTypeCatalogs.builtInSources()` 读取 `BuiltInRegistries.RECIPE_SERIALIZER` 和 `RECIPE_TYPE` 的 keySet，包含已经注册的模组条目。配方 JSON 的 `type` 对应 serializer ID；原生 `Recipe#getType()` 是另一维，脚本 filter 的 `type` 与 `recipeType` 也分别查这两个表。[共同来源](<../../src/main/java/com/tkisor/nekojs/js/type_adapter/RegistryTypeCatalogs.java#L23-L39>)、[取 ID](<../../src/main/java/com/tkisor/nekojs/js/type_adapter/RegistryTypeCatalogs.java#L114-L118>)、[NeoForge](<../../src/main/java/com/tkisor/nekojs/api/NeoForgeCatalogPlatformProvider.java#L68-L78>)、[Fabric](<../../src/fabric/java/com/tkisor/nekojs/fabric/FabricCatalogPlatformProvider.java#L81-L90>)、[过滤器](<../../src/main/java/com/tkisor/nekojs/api/recipe/RecipeFilter.java#L153-L170>)。
- **自动 schema 是 NeoForge 上的启发式，不是 JSON 契约发现。** 两个 Minecraft 世代都在服务端资源重载监听入口尝试一次：遍历所有已注册 serializer，从 `serializer.codec()` 尝试反射字段；原版 shaped/shapeless 按已注册身份特判，未提取到字段时按名字猜，外层异常才降为单个必填 `json` 字段。通用层生成脚本定义；优先级为脚本 > 数据 > 插件 > auto。Fabric 有原生 ID 目录和配方处理，但没有这条 NeoForge scanner 路径。[1.21.1 入口](<../../versions/1.21.1/src/main/java/com/tkisor/nekojs/listener/ServerEventListener.java#L224-L236>)、[26.x 入口](<../../src/main/java/com/tkisor/nekojs/listener/ServerEventListener.java#L257-L268>)、[扫描](<../../src/main/java/com/tkisor/nekojs/api/recipe/definition/MinecraftRecipeSchemaScanner.java#L1-L4>)、[serializer 与降级](<../../src/main/java/com/tkisor/nekojs/api/recipe/definition/MinecraftRecipeSchemaScanner.java#L34-L76>)、[字段猜测](<../../src/main/java/com/tkisor/nekojs/api/recipe/definition/MinecraftRecipeSchemaScanner.java#L118-L187>)、[定义与优先级](<../../common/src/main/java/com/tkisor/nekojs/api/recipe/definition/RecipeSchemaAutoDiscovery.java#L22-L58>)、[合并](<../../common/src/main/java/com/tkisor/nekojs/api/recipe/definition/RecipeTypeDefinitionStorage.java#L21-L33>)。
- **真正的 JSON 兜底是绕过 schema，不是绕过 codec。** 自动 schema 的 `json` 字段写到同名路径，不会展开到根。在命名空间调用没有匹配的 handler/schema 时，一个 JSON 对象可直接回退到 `custom`，把 serializer ID 写入根级 `type`；也可显式调用 `event.custom(type, json)`。回退不预查 serializer，脚本重放的最终校验仍由带 `RegistryOps` 的 `Recipe.CODEC.parse` 完成，成功后才替换配方集合。[字段写入](<../../common/src/main/java/com/tkisor/nekojs/api/recipe/RecipeSchemaHost.java#L65-L80>)、[命名空间回退](<../../common/src/main/java/com/tkisor/nekojs/wrapper/RecipeNamespaceProxy.java#L119-L122>) [实现](<../../common/src/main/java/com/tkisor/nekojs/wrapper/RecipeNamespaceProxy.java#L195-L209>)、[custom](<../../src/main/java/com/tkisor/nekojs/wrapper/event/server/RecipeEventJS.java#L633-L649>)、[Fabric 共用 mixin](<../../src/fabric/resources/nekojs-fabric-shared.mixins.json#L5-L11>)、[提交](<../../src/main/java/com/tkisor/nekojs/mixin/RecipeManagerMixin.java#L210-L238>)、[解码](<../../src/main/java/com/tkisor/nekojs/mixin/RecipeManagerMixin.java#L356-L379>)。

## 原生注册表：三个独立条件

1. **表发现。** 当前 STARTUP 目录 `RegistryInfosPoint` 扫原版 `Registries`、插件贡献的 holder 类和手工条目，不枚举原生根表；反射到键只表示有元数据。另一个 `RegistryAutoAdapterScanner` 只扫描传入 holder 的 public static 字段，从泛型提取目标类型，或尝试用键查根表；两端内置只传 `BuiltInRegistries` 和 `Registries`。输出是把 ID 转成**已有**对象的 `SimpleRegistryBasedAdapter`，不是写入能力或 Builder。它在 Plugin Runtime bootstrap 中运行，早于 STARTUP 脚本，不能当作模组静态表的完整清单。[目录](<../../src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryInfosPoint.java#L42-L99>)、[扫描](<../../src/main/java/com/tkisor/nekojs/js/type_adapter/RegistryAutoAdapterScanner.java#L44-L86>)、[根表解析](<../../src/main/java/com/tkisor/nekojs/js/type_adapter/RegistryAutoAdapterScanner.java#L99-L126>)、[只读转换](<../../src/main/java/com/tkisor/nekojs/js/type_adapter/SimpleRegistryBasedAdapter.java#L64-L86>)、[NeoForge 调用](<../../src/main/java/com/tkisor/nekojs/core/NekoJSCorePlugin.java#L284-L291>)、[Fabric 调用](<../../src/fabric/java/com/tkisor/nekojs/fabric/FabricCorePlugin.java#L258-L266>)、[bootstrap → STARTUP](<../../common/src/main/java/com/tkisor/nekojs/core/lifecycle/NekoRuntimeAssembly.java#L112-L167>)。
2. **合法写入窗口。** NeoForge 不是在 mod 构造时向根表写，而是第一次收到 `RegisterEvent` 时收集一次，按随后每个事件的真实键 drain，load-complete 报告没等到 pass 的条目；过期的 pass 不能回放。上游 1.21.1 是先建原生表再发注册事件。Fabric 则在 NekoJS 自己的 initializer 加载 STARTUP 后立刻 drain，按待处理键查根表、缺表报错、存在才尝试 `Registry.register`；这不保证其他模组已经初始化，也不保证根表里每张表都可写。[NeoForge adapter](<../../src/main/java/com/tkisor/nekojs/listener/RegistryEventAdapter.java#L61-L76>)、[上游顺序](https://github.com/neoforged/NeoForge/blob/1.21.1/src/main/java/net/neoforged/neoforge/internal/CommonModLoader.java#L52-L54)、[不可回放](<../../src/main/java/com/tkisor/nekojs/wrapper/registry/gen/StartupRegistryRuntime.java#L146-L152>)、[Fabric 入口](<../../src/fabric/java/com/tkisor/nekojs/fabric/NekoJSFabricMod.java#L129-L141>)、[Fabric drain](<../../src/fabric/java/com/tkisor/nekojs/fabric/FabricRegistryAdapter.java#L71-L119>)。
3. **对象工厂或 codec。** 已有 Builder factory 时可以沿用 `RegistryTypesPoint` 的默认或命名类型；只有可信的、针对该表条目的官方 codec 时，才有条件提供 JSON 入口，还需正确的 RegistryOps 和生命周期。若只知道 `T`，就只发现/显示表键；不猜构造器或承诺 `create(id, json)`。当前低层 supplier 入口仍须调用方自己提供对象，并不自动制造对象。[工厂目录](<../../src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryTypesPoint.java#L47-L91>)、[supplier 入口](<../../src/main/java/com/tkisor/nekojs/wrapper/registry/gen/RegistryEventJS.java#L184-L208>)。

**数据包注册表另走 SERVER/资源加载。** 例如 KubeJS 2101 的 STARTUP handler 由 NeoForge 的实际 `RegisterEvent` 键驱动；它的 SERVER 数据表则在 `firstLoad` 枚举 `DataPackRegistriesHooks` 并使用上游 `elementCodec`，而不是拿静态表键猜 codec。这说明可借鉴的是上游提供的表键及条目契约，不能把数据包表混入 STARTUP。[KubeJS 静态 pass](<D:/kubejs-2101/src/main/java/dev/latvian/mods/kubejs/registry/RegistryEventHandler.java#L23-L57>)、[KubeJS 数据包路径](<D:/kubejs-2101/src/main/java/dev/latvian/mods/kubejs/server/ServerScriptManager.java#L183-L227>)。

**若后续扩展：** 订阅时先校验并规范化键的形状，不以 bootstrap 快照断言缺表；到加载器首个合法写入时点再验证表的存在和支持能力，明确区分缺表、未有/错过 pass 和无工厂。Probe 可用同源、按 loader/版本生成的发现快照补全，但补全不授予写入能力。以上仅为源码调查；没有修改执行路径或验证实机、自定义表与 Fabric 模组初始化顺序。
