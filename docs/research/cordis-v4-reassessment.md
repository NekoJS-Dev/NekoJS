# NekoJS 采用 Cordis v4 理念：实现范围与路线

**修订结论：四项需求已由维护者确认需要，应建设动态能力依赖、作用域实例、结构化资源生命周期和受管模块局部重载。** 实现以现有 NekoRuntimeRoot、插件收集模型和候选事务为基础，将 Cordis 的理念落实到 Java/GraalJS 运行时。

本文是待审阅的实现范围与建议契约，不表示相关能力已经实现，也不冻结新接口的名字。维护者确认的是功能需求；“已经反复发生资源泄漏”及“已经测得整代 reload 不可接受”仍没有本次调研证据。性能基线和具体故障验证列入第一阶段工作，不再作为是否需要这四项能力的前提。

## 1. 已确认的目标

| 编号 | 必须实现的行为 | 一个可观察的例子 |
|---|---|---|
| G1 动态依赖 | 运行中的脚本包可以提供能力；其他包声明依赖，随能力出现、消失或替换自动激活、停用或重建 | economy 退出后，依赖它的 shop/quests 自动停止相关功能；恢复后重新激活 |
| G2 作用域实例 | 同一能力可在不同世界、会话和包中绑定不同实例，并只替换指定范围的实例 | 替换世界 A 的 economy，不影响世界 B 或测试环境的账本 |
| G3 资源归属 | 长期资源在创建时登记 owner；初始化失败、正常退出、子模块退出和重入情况下都能确定地清理 | 包退出后，其监听器、timer、watcher 和子模块不会继续工作 |
| G4 局部重载 | 根据代码依赖和能力依赖计算受影响集合；在支持的副作用范围内准备候选并替换该集合 | 修改 economy 时只替换 economy 及受影响依赖者，无关的 chat 模块不重跑 |

G1–G4 都在最终交付范围。阶段性只交付资源管理不能宣称整体完成；明确的模块局部重载不能一直以整代重载代替。

## 3. 先统一实现中的几个概念

以下是本方案的工作用语；落地时与 CONTEXT.md 的既有术语对齐，不在本次直接改领域词典。

| 概念 | 在方案里的含义 |
|---|---|
| 能力契约 | 能力的标识、版本、操作与输入输出约束；不是某个正在运行的对象 |
| 能力实例 | 在指定作用域内，由某个运行单元提供的可用实现；包含提供者身份和激活版本 |
| 运行单元 | 能独立准备、激活、停止和替换的脚本模块；默认可以是包在某个 ScriptType 下的入口集合，也允许包显式拆分子模块 |
| 作用域 | 决定能力在哪里可见、解析到哪个实例；必须带具体世界/会话实例身份 |
| 资源 owner | 负责资源最终关闭的对象；子资源必须有唯一归属 |
| 激活实例 | 运行单元某一次启动的实例；同一模块替换前后属于不同激活实例 |
| 替换批次 | 一次事务同时准备和交接的受影响单元集合 |

运行单元不等同于任意一个 ESM 文件，也不等同于现有 ApiModuleDescriptor 中的 API 模块。代码依赖图描述“哪些文件被引用”，能力依赖图描述“哪些运行实例必须共同存活”，资源归属树描述“退出时谁关闭谁”；三者分别维护。

现有 ScriptPackScope 的 GLOBAL / WORLD / SERVER_CACHE 带有包来源和加载生命周期含义；EnvironmentScope 主要筛选 ScriptType、loader、版本与模组。这两者都不能单独充当运行中的 world/session 实例 ID。

## 4. 需要实现的工作包

### M1. 运行单元描述与作者入口

- 扩展包描述，表达稳定的模块 ID、入口集合、能力提供/依赖、作用域、契约版本和支持的重载方式。身份至少区分包来源、包 ID、ScriptType、运行作用域实例、模块 ID，避免同名世界包互相覆盖。
- 新增受管的激活入口：只有依赖解析和配置验证通过后，才执行该入口；同一次激活只调用一次。停用后再恢复是新激活，不是从中断位置继续执行。
- 让 JS/TS 脚本包和 Java 插件提供的 Adapter 都能取得受限的依赖视图与资源登记入口。沿用 Event Group / Binding / Builder 的脚本作者风格，接口名字和 manifest 字段在原型验证后确定。
- 新契约字段不得沿用旧 manifest 的“类型不符就默认值”来静默忽略坏依赖。校验错误应定位到包、模块、能力及字段。
- 旧包缺少新描述时走现有加载语义；提供迁移说明，将愿意参与局部重载的包转为受管运行单元。

**验收：** 一个包能声明 economy 提供者和奖励子模块，另一个包能依赖 economy；坏声明在激活前失败，旧包仍能按既有入口运行。

### M2. 作用域能力实例与解析规则

- 区分“静态契约可用”和“当前作用域内已有活跃实例”。已有平台能力作为受控的 root/环境提供者接入；动态实例不绕过 CapabilityDefinition 的版本、环境和提供者策略。
- 实现世界、会话、包级实例身份及显式可见性。世界与网络会话不是强制的一条父子链；由装配确定合法的父作用域，禁止自动跨兄弟世界或无关会话查找。
- 建议解析规则：沿声明允许的作用域链查找最近的有效绑定；同层重复提供者报错；覆盖父级实例必须明确声明。已选择的局部实例失效时不能悄悄改用另一世界或更外层的实例。
- 能力撤回、提供者身份/激活版本变化、局部覆盖变化都通知实际受影响的使用者；即使能力名称不变，更换实例也要使旧引用失效或驱动依赖者重建。
- 脚本包 owner 不能假冒 Java 插件身份取得 CORE_ONLY 能力。沿用包验签、信任和环境权限；“能看见名称”不等于“获准调用”。
- 提供者异常退出后，旧句柄不得继续调用已关闭的 Context；错误应明确指出能力不可用或句柄已过期，不自动转发到身份不相同的新实例。

**验收：** 世界 A/B 各有 economy，替换 A 只影响 A；断开会话后旧句柄失效；重复提供和越权覆盖被拒绝。

### M3. 动态依赖图与启停协调

- 记录模块声明及实际解析到的提供者，建立反向依赖；缺失或版本不兼容时进入可诊断的等待状态。环在激活前拒绝并给出依赖路径，不让模块无声地永远等待。
- 提供者 ready 后按依赖顺序激活消费者；停用时先禁止新调用、排空或取消已有工作，消费者先退出，仍可用的提供者最后释放。
- 管理员禁用与暂时缺依赖分开记录：禁用者不因能力恢复自行启用；暂缺依赖者恢复后自动重新激活。激活失败进入失败状态，只有相关输入变化或显式重试才重试，避免每 tick 重启风暴。
- 同一 ScriptType 的生命周期仍由既有 owner 路径串行调度，close 优先。把多个同时发生的变化合并成一轮目标状态协调，提交前复核依赖版本，避免过期候选提交。
- 依赖局部替换和包卸载走同一协调入口，禁止命令、监听回调、文件 watcher 各自维护一套启停顺序。

| 场景 | 必须采用的失败语义 |
|---|---|
| 正常热替换，旧提供者仍健康 | 先准备新提供者及受影响消费者，候选失败保留整组旧实例 |
| 提供者实际失效、连接断开或信任撤销 | 立即阻止新的依赖调用并停用消费者；不能声称保留旧实例就恢复了已经失效的外部能力 |
| 缺失能力重新出现 | 对仍启用的等待模块重新解析并激活，不恢复上一轮进行到一半的业务操作 |
| 任一方正在关闭时又收到 reload | 按生命周期门拒绝或合并到合法的后续请求；不递归启动第二个候选 |

**验收：** economy → shop/quests 的停启、恢复和替换都由依赖协调触发；无关 chat 的实例与初始化次数不变；出现环与激活失败时能查询具体原因。

### M4. 资源归属与确定性释放

- 复用 ResourceTracker 的幂等、逆序、失败继续清理与异常汇总基础，将资源获得与登记放在同一受管操作中；初始化到一半失败时，已经获得的资源必须释放。
- 区分 root、世界/会话、包和激活实例的 owner。一个资源只有一个最终 owner；借用共享能力不能取得关闭它的权利。generation 退出不能关闭 root 资源。
- 事件、timer、watcher、执行任务、连接和子模块都提供受管登记与释放方式。已有资源优先接入；新资源类型沿同一入口扩展，无需每次修改所有 reload 出口。
- 生命周期顺序至少包括：禁止新工作、取消/等待在途工作、关闭依赖消费者与子资源、关闭本实例资源。timer/Context/流等已有先后约束必须保持；按依赖排序不能简单等同于整棵树全局 LIFO。
- 异步清理必须可等待且不阻塞 MC owner thread。关闭期间迟到的初始化结果要立即回收，迟到 callback 不得发布到新实例；清理失败继续执行其他清理并保留诊断，不把未完成清理报告成成功关闭。等待设有明确期限；超时则隔离该实例、报告未释放资源，并阻止依赖同一独占资源的新实例启动，不强行把仍在运行的任务标记为结束。
- 状态需表达等待、准备、活跃、停止中、失败、已释放；用户的启用意图另存。重复关闭共享同一次完成结果，失败和取消保留原始原因。

**验收：** 每个资源最多关闭一次；半初始化失败、父退出、资源释放抛错和关闭时新增迟到资源都不遗留可执行旧回调；其他包的资源保持可用。

### M5. Graal 执行隔离与跨单元调用

这是局部候选替换的前置设计。当前 ScriptManager 持有单个 RuntimeEnvironment，多个脚本共享同一 ScriptType 的 Context。共享 Context 内重新执行代码可能修改 globalThis、模块缓存和可变对象，清理 token 并不能撤销这些修改。

- **建议默认方案：受管运行单元拥有可独立释放的 Graal 执行环境，先以独立 Context 原型验证。** 单元默认可按包划分，包内需要独立重载的模块可显式拆分。旧模式继续使用原环境；不为每个 import 文件无条件新建 Context。
- NekoRuntimeRoot 继续总持有，ScriptManager 保持每个 ScriptType 的调度职责；由一个环境扩展为受管实例集合不意味着新增第二个总运行时。整代 reload 是同一替换机制覆盖全部相关单元的情况。
- 跨 Context 的能力调用采用宿主侧受控句柄与明确的输入输出转换。不能假定把 Graal Value、JS 闭包或可变对象放进 Map 就能安全跨环境使用。
- 明确同步/异步调用、取消、错误传播、在途请求排空和旧句柄失效。跨 owner thread 不同步等待形成死锁；跨 ScriptType 的能力默认不直接注入 guest 对象，需要显式桥接。
- 保留既有 type-local global / 显式跨类型 shared 的含义；为受管模式定义可跨环境共享的数据与有期限的宿主句柄。无法安全迁移的 guest 对象不能静默复制或延长旧 Context 的寿命；迁移文档必须说明可用数据形状及限制。
- 重新核对 binding/schema、模块 session、source map、错误视图、watchdog、guest 状态清理及 isContextDead 等查询：要按实际激活实例定位，不能再用“等于该 ScriptType 唯一 active Context”作判定。

**验收：** 同一 ScriptType 下 A/B 同时存活；A 候选失败时旧 A/B 可继续调用；A 替换成功后旧 A 关闭，B 不重建；跨环境能力返回值和异常可预测且不泄漏旧 Context。

Context 粒度、互操作开销和内存成本必须在 P0 原型中测量。若独立 Context 无法满足契约，应修改执行隔离设计并保留 G4 目标；不能用共享 Context 中的非事务重跑冒充通过验收。

### M6. 局部替换事务与影响范围

- 使用文件依赖图找代码受影响入口，使用能力反向依赖找需要重建的消费者，再纳入共享不可拆分资源/领域计划要求的单元，计算一个闭合的替换集合。结果中说明每个单元为何被包含。
- 运行单元之间的业务协作走已声明能力；跨单元直接 import 若无法隔离，应合并为同一替换集合或明确拒绝该局部模式。动态加载也要记录实际依赖；无法确定影响范围时不得报告精确局部重载成功。
- 引入单元级激活标识。listener、timer、能力句柄、模块 session 和诊断一起指向对应实例；替换 A 不能使 B 因全局 generation 编号变化被误判过期。
- 将 ListenerBatch 和状态发布扩展为按 owner/激活集合替换。多个候选单元的 global/shared 顶层写集合并检查，与仍活跃单元的读写依赖及作用域版本复核后一起提交，不能逐单元发布出混合版本。
- 领域结果按 owner 保留贡献账目：移除 A 的声明后重算相关合并结果，保留 B 的贡献。恢复一个全局基线再只应用 A 的新计划会误删 B，不满足局部替换。
- 整代 reload 继续提供完整候选失败保留；新受管单元的文件 reload 接入局部候选路径。旧文件重跑路径保持明确的非事务标记，迁移后撤掉对应临时分支。

**验收：** 同时替换 economy 与它的消费者要么整组提交，要么全部保持旧实例；chat 的 Context、资源和非目标状态不变。

### M7. 平台生命周期、持久状态与兼容迁移

- 世界进入/退出、连接建立/断开、包启停/删除统一驱动 scope 创建、能力撤回与资源释放；同名世界重新进入或重连同一地址也要有新实例身份。
- 普通 reload 不销毁有意保留的 root 状态、配置、pdata、世界数据、pack 缓存或信任记录。持久数据迁移使用现有备份/原子替换机制，不能通过“退出即清空”解决资源归属。
- [PackSyncClient](../../common/src/main/java/com/tkisor/nekojs/core/pack/sync/PackSyncClient.java) 的验签、授权、缓存物理替换和回退流程继续生效；新增能力不可早于这些校验对外可见。
- STARTUP 游戏注册保持明确的不可逆约束；一个包可以同时有 STARTUP 初始化与支持局部替换的 SERVER/CLIENT 单元，重载结果必须区分需重启部分。
- Java 插件通过既有 Point / Plugin Hook / Contributor 安装契约和 Adapter。若新增收集通道，补齐 Point、Hook、内置清单与配对测试；不扩展为任意 Java mod/JAR 热卸载。
- 所有目标 loader/版本节点覆盖相同的运行契约。新增 Minecraft 相关操作通过现有版本 facade 或节点实现，common 保持无 Minecraft/loader 依赖。

**验收：** 切世界、重连、撤销信任及包更新失败后，scope、能力与权限一致；旧脚本作者面和持久数据没有范围外变化。

### M8. 诊断、性能与作者文档

- 可以查询单元状态、等待/失败原因、解析到的能力实例及作用域、反向依赖、资源数和当前激活版本；错误给出包/模块/阶段，沿用 NEKO- 诊断体系。
- reload 输出实际影响集合、局部/整代/拒绝结果、失败后保留的实例和清理失败。先利用现有命令/日志观察面，不以建设新 GUI 作为前置条件。
- 记录整代与局部重载的准备、执行、计划、提交、清理耗时及 owner thread 最长连续占用，比较同一负载下的重复样本、p50/p95 和峰值内存。
- 文档提供提供者/消费者、作用域覆盖、资源登记、失效恢复、局部替换失败保留的 JS/TS 示例；同步生成声明、Probe 与规范契约，避免实现与补全分离。

**验收：** 维护者能回答“模块为什么没启动”“调用的是谁”“为什么这次多重载了两个包”“旧实例是否清干净”；同一测试负载有可重跑的前后对照。

## 5. 一次正常局部替换必须经过的流程

1. **确定集合**：读取当前 scope/能力/源依赖版本，计算目标与消费者闭包；检查所有操作是否在支持范围。
2. **创建候选**：为集合内各单元分配独立候选环境和资源 owner。旧实例继续承担生产调用；候选能力只能被该事务的候选消费者解析。
3. **准备计划**：执行候选初始化，收集 listener、timer、能力发布和受管状态/领域计划。候选不提前接收生产事件，不向外发送未经允许的效果；调用仍活跃外部能力限于受管的查询或可暂存操作。
4. **联合预检**：检查依赖版本、scope 是否仍存活、共享状态冲突、领域计划和 close 请求。失败时销毁全部候选，健康的旧集合保持。
5. **交接**：在所属 owner 路径和规定的回调交接点发布一份新的活跃映射，成组切换能力、事件、timer 和状态。提交区不执行可能失败的任意脚本或阻塞 I/O。
6. **退出旧实例**：旧实例不再接受新工作；在途操作按契约排空/取消，旧消费者先于仍被它们使用的旧提供者释放。提交后的清理失败报告为“已提交但清理失败”，不能谎报候选失败且旧版本仍活跃。

本流程的原子范围是一个受支持的 owner/ScriptType 替换批次；不同线程上的 SERVER/CLIENT 不自动组成跨线程原子事务。跨类型业务若需要一致提交，需专门协议，不能由作用域查找隐含承诺。

现有 CandidateStatePlan.publish() 只约定预检后不得抛出，没有通用领域 undo。要参与局部原子替换，Adapter 必须把失败工作前移，提供真正的提交/恢复策略，或被标记为不支持该事务。不能仅增加一个 rollback 名字就宣称世界状态可恢复。

## 6. 副作用支持范围必须逐类交付

| 操作 | 局部替换的目标行为 | 实现要求 |
|---|---|---|
| 事件监听、timer、子任务、watcher | 支持受管创建、候选暂存、退出撤销 | token/任务挂到激活 owner，处理排队和迟到 callback |
| 动态能力提供与依赖引用 | 支持候选视图及整组发布 | 作用域实例表、依赖版本校验、旧句柄失效 |
| global/shared 顶层受管操作 | 保留已有数据语义并支持批次冲突检测 | 多单元联合写集、必要的读取依赖校验与客体寿命约束 |
| 领域声明，例如属性修改、交易等 | 逐个 Adapter 实现后才纳入支持 | 按 owner 保存贡献、验证合并和移除，保证未受影响贡献不变 |
| 共享可变对象的嵌套修改、跨 Context 裸 Value | 不承诺任意深回滚 | 受管模式在访问入口限制或转换，不能仅让作者在 manifest 自称可撤销 |
| 发包、发消息、任意文件/世界修改 | 已发出的效果不自动撤销 | 候选期间禁止或延迟；确需补偿时由领域定义，并明确其保证范围 |
| STARTUP 注册、不可逆 Java/平台操作 | 明确拒绝局部替换或报告需重启 | 不偷偷执行后把失败伪装成完整回退 |

借鉴 Cordis 的所有权模型不会绕过宿主约束。受管候选的受限接口必须能阻止已知旁路；需要任意 Java 访问的旧脚本可继续旧模式，但不自动获得局部事务保证。

## 8. 必须留下的端到端验收场景

| 场景 | 预期结果 |
|---|---|
| 先启用 shop/quests，后启用 economy | 消费者先等待；能力 ready 后各激活一次 |
| 主动停止 economy，然后重新启用 | 消费者自动停止并清理；恢复后重新激活；手动禁用的消费者不被复活 |
| economy 新版本或任一消费者候选报错 | 整个替换集合保留健康旧实例，候选资源无泄漏，chat 不受影响 |
| economy 的外部连接真的失效 | 新调用被拒绝，依赖者停用；恢复时新激活，不伪造旧连接仍可用 |
| 世界 A/B 同名能力，替换 A | B 的实例、数据、资源和调用次数不变 |
| 关闭包时资源释放报错，异步初始化随后完成 | 继续其他清理，迟到资源回收，残留/超时可诊断，无幽灵 callback |
| 替换 A，B 持有旧能力句柄或旧请求仍在途 | 按已定义的失效/排空契约处理，不访问已关闭的 Context，不混用新旧依赖 |
| 局部领域声明被删除 | 只移除该 owner 的贡献，其他单元与平台原有贡献保留 |
| 局部候选与活跃单元修改同一受管状态 | 冲突被拒绝或按既定规则解决，不丢失活跃单元已提交写入 |
| 世界退出、断线、close 与 reload 同时请求 | close/撤权优先，过期候选不提交，不跨 scope 激活 |
| 多轮局部替换与整代 reload 混用 | 回调无重复，旧 Context、token、任务和模块 session 不持续积累 |
| 旧包和受管包共存，尝试重载不可逆注册 | 旧行为保持；结果明确标注支持范围和重启要求 |

复用 ScriptReloadGenerationTest 等已有回归检查，在对应层补最小的故障注入和可观察行为测试。common 实现使用 `:common:check`；修改边界/源集时加 `guardLint`；公开契约检查配对与 golden；声明变更运行 Probe 类型检查；平台行为覆盖受影响节点的构建、GameTest/必要 smoke。具体命令按当前 CI 与 [coding conventions](../agents/coding.md#verification) 执行。

## 9. 改动落点和对外契约

| 落点 | 预计改动内容 |
|---|---|
| common/core/lifecycle 与 script | owner、激活实例、作用域生命周期、批次调度和 ScriptManager 改造 |
| common/core/pack 与 core/pack/sync | 运行模块描述、世界/会话实例和包启停/同步接入 |
| common/api/capability 与 core/api | 复用静态能力契约和策略；动态实例解析放实现层，确需作者使用的契约才进入 api |
| common/api/event、core/node、core/module、core/state | 精确资源归属、影响图、多个 Context/session 和批次状态计划 |
| 版本树及版本 facade | 世界/会话入口、受管平台效果和增量领域 Adapter |
| wiki、契约源与生成器、Probe、测试 | 新作者接口、迁移示例、错误码、声明与验收证据 |

以上是职责落点，不是要求每项都新建一套类。优先扩展现有模块；新公开接口只承载作者实际需要的能力，调度和状态机细节留在实现内。

- Script API：新增受管模块的声明、激活依赖和资源登记契约；现有 Event Group / Binding / Builder 继续使用。
- Plugin API：补充能力/资源 Adapter 的必要入口；只有新增收集通道才走 Point 配对流程。
- 包格式：新增描述需定义 schema/版本与旧包默认行为；若元数据进入同步包，要验证签名覆盖、完整传输与旧端兼容，不能只改本地解析。
- 状态与重载语义：受管单元可以独立替换，需公布共享数据限制、失败保留范围、旧句柄规则；普通旧包不被静默升级为事务模式。
- 暂时不在本方案内：任意 mod/JAR 热卸载、撤销已发出的网络效果、跨进程分布式事务、无条件热重载所有 STARTUP 注册。它们不属于已确认四项目标的必需前提。

## 10. 理论依据与原评估修正

[一手资料核查](cordis-v4-primary-sources.md)保留论文及固定提交源码证据。论文 [arXiv:2608.25512v1](https://arxiv.org/abs/2608.25512v1) 将可撤销效果与反应式依赖统一起来；它不验证作者的撤销函数，不自动回滚外部发出的效果，也不提供 NekoJS 的线程调度和候选事务。

当前方案采用其资源归属、依赖可用性和作用域组合理念，保留 NekoJS 的失败候选保留契约；无需引入 TypeScript 版 Cordis 包。所有权清理、动态依赖与事务替换需要合作，不能互相替代。

原评估中仍需保持的事实修正：generation 与 Fiber 只能类比，不能等同；Cordis 同一 effect 内能表达异步清理顺序；NativeEventsJS 有 unregister 且默认 STARTUP-only；ResourceTracker 尚未成为 generation 作用域；global/shared 有意保留的状态不应因为退出而全部清空。[初版材料](cordis-v4-fit.md)仅保留为历史参考，其中相反的表述不作为本方案依据；“未来有需求再考虑”的建议已由本文确认的目标取代。
