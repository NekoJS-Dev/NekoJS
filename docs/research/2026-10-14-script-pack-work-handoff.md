# NekoJS 脚本包改进：接手 AI 工作说明

日期：2026-10-14。用于交接包机制后续工作；本次仅整理任务，没有实施下面的新机制。

## 1. 任务目标和范围

将 NekoJS 脚本包做成易于创建、明确依赖、准确启停、可独立管理生命周期、可可靠分发的功能。减少作者依靠目录顺序和隐含约定组织功能的负担，集中包操作的状态与失败处理。

范围包括：包身份与状态、清单/入口/依赖、包操作、实例与资源生命周期、动态能力依赖、局部候选替换、包创建/校验/归档及现有同步接入。

**不包含 VS Code 插件、语言服务器、编辑器界面或其他编辑器扩展。** 包模板与创建/校验能力属于本任务，可以供未来工具复用。本次不新增 Java 插件项目；现有 Plugin Runtime / Point / Plugin Hook / Contributor 约束继续适用，必要接入按仓库约定处理。

这是建议路线的交接，不冻结新 manifest 字段、命令名称、版本语法或归档格式。接手 AI 应先形成具体契约和变更范围；对既有明确授权继续执行，对尚未确定的重大兼容变化交付可审阅方案后再处理。不要将本次“整理交接”误记成所有公开迁移已批准。

## 3. 必须保留的设计基础

- `NekoRuntimeRoot` 继续作为总运行时 owner。普通 reload 不重新 bootstrap Java Plugin Runtime，generation 关闭不释放 root 资源。
- 使用现有 Event Group / Binding / Builder 风格；包管理能力由小而连贯的接口提供，准备、调度、授权、清理和提交留在实现内部。
- GLOBAL / WORLD / SERVER_CACHE 表达文件来源；世界/会话/包激活实例身份另行明确。包 ID、来源、激活版本和实例不能混成同一个字符串或 enum。
- 包版本依赖、代码 import 依赖、运行中能力依赖分别记账；资源归属描述谁负责关闭。它们共同决定受影响集合，不做一个万能 resolver。
- 保留 owner-thread、close 优先、候选失败保留健康旧代、受管状态冲突检测。STARTUP 及其他不可逆效果明确报告支持范围与重启要求。
- 保留 HostAccess/ClassFilter、路径/reparse 检查、签名、key pin、远端授权和旧缓存保护。来源 Adapter 不自行创建或激活 Context。
- 优先扩展现有模块；新入口应集中拥有操作与失败处理，避免再加一层逐个暴露 Registry/Cache/Trust/Context 的透传门面。

已有 [Cordis 路线](cordis-v4-reassessment.md) 记录四项目标：动态能力依赖、作用域实例、资源归属、受管局部重载。本任务以脚本包为具体落地场景，不撤销这些目标，也不把它们写成当前已实现的能力。

## 4. 建议按顺序完成的工作

### 阶段 A：统一包身份、状态和操作结果

处理：

- 定义可区分来源和实际实例的包身份；跨 GLOBAL/WORLD 同名可准确选择，远端活动包可查询。
- 将用户启用意图、已发现快照、实际活动实例、等待依赖、失败原因和待生效变化分开表达。状态名由契约草案确定。
- 集中刷新、校验、启停和重载请求的操作流程；命令、世界/连接生命周期和网络接线提交请求并读取最终结果。
- 修复状态保存失败仍报告成功的路径；明确 WORLD 编辑和启停何时刷新、何时生效。
- 查询执行计划，说明包顺序、入口和阻止激活的原因；来源 scope 不需要作者自行协调多套 owner。

落点优先：`ScriptPackRegistry`、`ScriptPackState`、`NekoJSCommands` 各节点、`ScriptManager.discoverWithPacks`、root 与连接/世界装配路径。

**完成条件：** 同名来源选择准确；保存失败不报成功；显示配置状态不会冒充实际活动状态；本地/世界/远端入口遵循一致结果契约。

### 阶段 B：明确清单、入口、库和依赖

处理：

- 设计带版本的新包描述及严格字段校验，错误定位到包和字段；发布机器可读 schema/规范，以便未来创建工具共用。
- 明确运行入口与库文件，避免扫描到的工具文件意外成为独立入口；说明文件是否执行一次、由谁加载。
- 定义包依赖及必要环境依赖、版本范围、重复身份、缺失/不兼容/循环依赖的处理和确定性排序。
- 依赖存在与执行先后是不同条件；现有 `priority/after` 的文件语义与包契约如何共存必须明确。
- 如提供跨包导出或服务入口，明确可见性、允许的数据形状、声明/类型生成和激活身份；它不等同于任意共享 guest 对象。
- 旧目录包、平铺目录、宽松 manifest 和现有导入路径有明确兼容/迁移方案；不静默替换旧包 Context/global 行为。

落点优先：`ScriptPackManifest`、`ScriptLocator`、`ScriptContainer`、`ScriptLoadOrderSorter`、`NekoModuleResolver`、现有 API surface 和声明生成路径。

**完成条件：** 新描述错误在激活前可诊断；入口与库按契约运行；依赖缺失、环、版本不符和排序均有确定结果；旧包在承诺范围内保持原行为。

### 阶段 C：包实例、资源归属和动态能力协调

处理：

- 定义包在 ScriptType、具体世界/会话下的激活实例，区分身份稳定部分与每次激活版本。
- 验证 Context 粒度与数据桥。先做两个独立实例互调、候选失败、关闭互不影响的最小原型，记录资源成本；不凭别的项目创建多个 Context 就直接转换旧包。
- 将事件、timer、任务和必要宿主资源归属到实际激活实例。半初始化失败、正常停用、重入、异步迟到和关闭错误都有清理结果。
- 实现能力提供者出现、撤回、失效、恢复、替换时对消费者的协调；管理员禁用不被依赖恢复自动撤销。
- 世界/会话关闭后旧句柄失效，不能跨兄弟世界查找或继续访问关闭的 Context；授权与能力可用性分别校验。
- 在已有生命周期路径中串行协调，消费者先停止，再释放仍被借用的提供者；异步清理有完成、超时和未释放资源的可观察结果。

落点优先：root、`ScriptManager`、`ScriptLifecycleGate`、`ResourceTracker`、Event Bus/timer、能力契约及世界/连接装配。复用现有静态能力规则，动态实例状态放在其真实 owner 内。

**完成条件：** economy → shop/quests 的等待、停止、恢复和替换正确；世界 A/B 隔离；被禁用消费者不复活；旧句柄不可用；异常与迟到资源按所有权回收。

### 阶段 D：真正的包局部候选替换

处理：

- 从代码依赖、能力消费者和不可拆分资源/领域要求计算受影响闭包，并给出每个包被纳入的原因。
- 在候选视图准备整个集合，联合校验受管状态、监听器、timer、领域计划与依赖激活版本；owner-thread 单次交接。
- 健康旧集合在候选失败时继续可用；提供者本身已经失效时，按实际失效契约停用消费者，不能假称旧实例保留就恢复能力。
- 无关包不重新初始化；未知影响范围明确拒绝精确局部模式或报告受控扩大集合。
- 与现有整类 reload、文件 active-context 重跑、STARTUP 回退的关系和迁移必须明确；不把文件重跑改名就当作局部事务完成。
- 世界退出、断线、close 或授权撤销抢占时，过期候选不能提交。

落点优先：现有 module dependency graph、candidate state/domain/listener 计划、generation 提交与资源释放路径。

**完成条件：** 更新 economy 时仅重建必要消费者，chat 不重跑；任一候选失败保留健康旧集合且候选资源清理；共享写冲突、删贡献、旧句柄和 close 抢占均有正确结果。

### 阶段 E：创建、校验、归档及分发接入

处理：

- 提供包核心的创建/校验入口和权威模板：输入最少信息即可生成合法清单、所选类型的示例和必要目录；具体命令名不在本交接中冻结。
- 模板、schema、解析与校验源保持一致；路径/ID 冲突可诊断，保留既有用户文件。现有工作区配置生成按原有内容保护规则接入。
- 契约稳定后定义一个简单的包归档和构建/安装流程。可重复构建、内容清单、库与依赖如何携带、升级/回退及删除内容都明确。
- 复用现有缓存暂存、恢复、哈希与签名机制；归档路径遍历、符号链接、文件数量和体量限制保留。
- 包内容与本机启用状态分离；签名及 SERVER_CACHE 内容保持不可改写，创建配置应在签名前完成或采用明确外置方案。
- 保留服务器信任和签名 key 规则；`allowUnsigned` 的校验/授权语义不一致单独验证并形成契约决定，不绕过远端授权。
- 将现有同步、断线、切服、同桶替换和配置阶段执行接入统一包生命周期；脚本包传输与动态注册表 prepare/ACK/commit 协议仍分层。
- `assets/data` 内容携带与各平台实际挂载分别说明和验收；完整新增 Fabric 资源桥不自动纳入这次包任务，需按明确的平台目标划定范围。

落点优先：包描述/来源实现、`WorkspaceGenerator`、`PackHasher`、签名、`ServerPackCache`、`PackSyncClient/Server`、平台接线及资源挂载。

**完成条件：** 创建包可直接运行示例，坏包可准确诊断；所需内容完整且构建可重复；安装失败正确恢复；切服/撤权不回退本地信任；旧 wire 和签名格式在未批准迁移范围内保持。

这里交付的是包核心能力。VS Code 插件、在线包市场、自动依赖下载和 Forge/NeoForge/Fabric 模组 JAR 生成器均不是本任务的默认交付物。

## 5. 待决契约：接手 AI 应具体化

| 决策 | 必须说明的选择依据 |
|---|---|
| 新描述版本与兼容模式 | 旧清单默认语义、新字段严格程度、未知字段、迁移和签名影响 |
| 入口/库/跨包导出 | 一次执行含义、导入路径、支持语言和声明、允许数据及关闭后行为 |
| 依赖版本语法与作用范围 | 包与平台条件、排序、同名来源、可重复解析；不默认照搬 npm 或 Maven 全套求解 |
| Context 和激活粒度 | 隔离目标、guest 对象寿命、线程、共享状态兼容、候选视图及资源成本 |
| 局部替换与不可逆效果 | 闭包、失败保留范围、领域支持、未知依赖和重启要求 |
| 归档与安装格式 | 内容范围、签名与 hash、外部库、升级恢复；不默认更换现有网络协议 |
| 公共查询/创建/管理入口 | 作者需要的最少操作，命令和机器可读结果；接口名仍待设计 |

这些选择形成一份可审阅契约，不以“先加几个类再决定”代替。既有授权记录与代码事实优先于历史研究建议。

## 6. 验证与完成标准

按维护者要求，源码与契约先收敛，阶段收尾/提交前集中验证，不因每次小改动重复整套矩阵。必要的最小诊断或原型验证单独标记用途，保留真实失败，不作为最终验收通过。

按改动复用现有包 Registry/Locator、排序、模块 resolver/identity、generation/reload、世界包、签名/缓存/同步和 WorkspaceGenerator 测试。验证命令与节点配置查当前 [CI](../../.github/workflows/ci-build.yml) 和 [verification](../agents/coding.md#verification)，common 改动包含 `:common:check` 的隔离检查。

每个实现阶段应交付：

1. 最终变更范围和真实调用链；公开、持久化和 wire 变化分别说明。
2. 对外行为、兼容/迁移和必要作者文档；改 canonical 源再生成声明/golden，逐项解释差异。
3. 适当单元与隔离检查、受影响节点构建；实际 MC/网络/资源变化补真实环境验证。
4. 精确源码/制品绑定的结果，区分 PASS、FAIL、NOT_RUN；失败保留与故障恢复有证据。

最终包任务必须证明：创建入口可用；依赖和执行计划可诊断；启停状态准确；四项生命周期目标有端到端证据；安装/分发在所承诺范围内可靠；文档与实际行为一致。局部阶段通过不等于整体完成。

性能比较使用相同脚本/环境、固定门槛和精确 revision，保留首样本和 warmup，不能把架构简化直接记成性能提升。完整 IDE 问题及旧总任务未完成项按真实状态记录；包任务没有自动继承历史完整验收。维护者接受须记录其实际结论，不能代签。
