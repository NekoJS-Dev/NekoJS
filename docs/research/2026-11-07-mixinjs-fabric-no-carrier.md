# Fabric Loader 0.19.3: MixinJS without an independent carrier mod

Date: 2026-11-07. Research-only GPT subagent report. No implementation, Gradle build, Minecraft launch, or executable probe was performed.

## Recommendation and confidence

**An independent Fabric carrier MOD is not demonstrably necessary.** The pinned sources support a plausible internal route: a static NekoJS-owned Mixin config, an embedded standalone `IMixinConfigPlugin`, internal Knot classpath admission of a previously generated immutable cache artifact, and `getMixins` dynamic enumeration. Prioritize a minimal real-launch experiment for this route; retain the implemented carrier until it passes.

The precise timing hypothesis needs correction: **`IMixinConfigPlugin.onLoad` is not called during ordinary `FabricMixinBootstrap.init` registration before DEFAULT.** Registration parses the config; plugin construction/onLoad occurs when the transformer selects it. Initial selection prepares the plugin's dynamic mixins before applying mixins to the class initiating selection. This can avoid late-preLaunch registration limitations without requiring a before-DEFAULT callback. [F1–F3, M1–M3]

| Promise | Assessment |
| --- | --- |
| No additional mod-list entry | Source-backed internal feasibility: classpath code source is not a mod container. No live proof. |
| No separate JAR | An immutable exploded directory is plausible too, but remains a separate artifact. The recommended JAR variant retains an internal cached JAR. |
| No additional bootstrap installation | Plausible: config/plugin are inside ordinary NekoJS. No agent, launcher patch or second bootstrap mod is required by this path. |
| Pure in-memory generated bytecode | Not established; the selected provider resolves class/resource streams, not a plugin-supplied byte array. |
| Public supported API | No. Dynamic enumeration is a Mixin extension contract; `FabricLauncherBase`/`FabricLauncher.addToClassPath` are Fabric implementation APIs. |
| Already operational / production-ready | No. This report establishes pinned-source feasibility, not runtime or production acceptance. |

## Actual timing: why this is stronger than late preLaunch

`Knot.init` performs loader load → freeze → class tweakers → `FabricMixinBootstrap.init` → `finishMixinBootstrapping` → transformer initialization → game classpath unlock → `unlocked = true` → invoke preLaunch. `finishMixinBootstrapping` advances INIT then DEFAULT. [F1, F3]

`FabricMixinBootstrap.init` calls `Mixins.addConfiguration` for each metadata config and decorates its handle. DEFAULT is the fallback config environment. Plugin invocation occurs in `MixinConfig.onSelect`, reached from the transformer's `selectConfigs`, not at registration. Preparation completes before the current target's mixins are collected/applied. [F2, M1–M3]

Under the ordinary sequence this means after DEFAULT, on initial applicable transformation, normally before a preLaunch entrypoint body if loading that implementation initiates transformation. It is not a guaranteed independent “before all preLaunch” lifecycle event: the initiating class and installed mods vary. A PREINIT-only config or private phase mutation is not the solution.

The old `unvisitedCount > 0 && transformedCount == 0` restriction concerns subsequently registered configs. Here the static config is already selected and `getMixins` contributes to its current preparation. No second selection is needed for those names. [M2, M3]

There is no promise for already-defined targets. Custom language adapters are instantiated before transformer initialization; they or other bootstrap code can load targets too soon. `MixinInfo.readDeclaredTargets` checks for loaded targets and throws for a required config. [F4, M6]

### Bootstrap isolation and the early-bytecode guard

`PluginHandle` loads the plugin through the service class provider and Knot target loader, not an arbitrary private child loader. Mixin explicitly warns that plugins run inside transformer/bootstrap code and must not reference game or ordinary mod classes. Nested loads during preparation suppress normal selection and can fail with `ReEntrantTransformerError("Re-entrance error.")`. [F7, M3–M5]

Embed the plugin/helpers outside all owned mixin package roots. Keep them JDK plus deliberately chosen Loader/Mixin bootstrap types; parse only a small bounded selection manifest. Do not initialize Graal, `NekoRuntimeRoot`, ordinary platform facades, game targets or generated mixin classes. Do not use `Class.forName` to “register” generated mixins: Mixin reads their classfile bytes. Put dispatch helpers outside the mixin-only package because ordinary classloading in an owned mixin package is rejected. [M3, M6]

Knot's bytecode-provider method throws `IllegalStateException("early getClassByteArray access")` until the launcher unlock flag. Thus the initially assumed before-DEFAULT timing would actually be problematic for arbitrary target-bytecode access. The normal `MinecraftGameProvider.unlockClassPath` body only adjusts paths/prefixes, with no direct target load, but real-launch instrumentation must still establish the exact first-selection/unlock ordering. [F5, F8]

## Recommended candidate mechanism — not implemented

1. Register one unique static NekoJS-owned config with an isolated nonempty generated-mixin package root and embedded standalone plugin. Prefer empty static mixin lists: plugin load failure is logged and can leave the plugin absent, so no unconditional generated entries should remain.
2. Generate/validate classes outside transformation, on the previous launch or offline. Put immutable content-addressed JARs or directories outside the mod discovery directory. Include generated mixins, out-of-mixin-package helpers, the selected plan and optional refmap. No independent Fabric metadata is required for the classpath operation.
3. In `onLoad` validate Loader/Mixin pin, physical Minecraft identity, side, namespace, plan/ABI/hash, disabled selection and development-only policy; check path confinement and bounded metadata. Only then call internal `FabricLauncherBase.getLauncher().addToClassPath(path)`. This is not an invitation to add arbitrary paths from untrusted cache pointers.
4. In `getMixins` return only approved side-specific names, relative to the static package. `prepareMixins` concatenates `this.mixinPackage + mixinClass`; an unrelated fully-qualified name is not a substitute. A reserved fixed root plus valid hash-qualified suffix such as `h<hash>.Hook0` can preserve class identity. Apply safety filtering here because these entries bypass shouldApplyMixin. [M2, M6]
5. Preserve an immutable bootstrap admission receipt for later runtime consumption. Later code must validate the exact admitted plan, not scan arbitrary cache files as trusted installed hooks.

This is not completed NekoJS integration. [IPlatform plan visitation](<../../common/src/main/java/com/tkisor/nekojs/platform/IPlatform.java#L63-L64>) describes native-admitted mod resources; [MixinCarriers](<../../common/src/main/java/com/tkisor/nekojs/core/mixin/MixinCarriers.java#L19-L46>) requires the synthetic mod ID to match the plan hash. A classpath-only artifact has no such owner container. Adapt the admission evidence deliberately while preserving “only actually admitted plans become runtime hooks”; do not weaken owner/hash checks into a raw cache scan.

### Why not recursively add generated configs?

`MixinProcessor.selectConfigs` iterates the live `Mixins.getConfigs()` set, removes a selected handle, then calls its `onSelect`. `Mixins.registerConfiguration` adds to the same `LinkedHashSet`. Recursive `Mixins.addConfiguration` from plugin onLoad can invalidate the iterator when more elements remain, or leave the newly added handle unselected in the current pass when no further advance occurs. Registering in getMixins happens after that selection loop and also does not enroll the config into its current pending set. Later selection again depends on transformed-count state. [M1, M3]

Dynamic enumeration directly adds definitions to the selected parent config and avoids this live-collection mutation. Also, plugin `acceptTargets` occurs before `postInitialise/getMixins`; do not assume that callback already sees the dynamic additions' target set. [M2, M3]

## Visibility, loader reachability and metadata

`KnotClassDelegate.addCodeSource` normalizes an existing Path, records the code source and adds its URL to the target loader. It does not parse metadata. Raw bytes are found through the loader's local resource URL first and then permitted parent fallback, and read with a resource stream. `MixinServiceKnot` uses this same target loader/provider. That supports metadata-free JARs or directories for both Mixin bytecode reading and ordinary helper/resource linkage. [F5–F7]

Attach the source to Knot, not a private child loader or only the thread context loader. Parent fallback has code-source isolation; a system-classpath accident is not proof. This URL admission path performs no named-module graph mutation; NeoForge module-layer constraints should not be imported into it. Duplicate class definitions remain hazardous. [F6, F7]

`FabricLoaderImpl.addMod` separately populates mods/modMap. Adding a code source does not call it, so there is no new Fabric container/mod-list entry, dependency resolution, entrypoint or metadata-driven class tweaker for the cache artifact. The static config remains decorated with NekoJS's mod ID/compatibility although generated classes have a different physical code source. No equality check tying these generated bytes to that mod container was found in the cited preparation path. [F2, F4, M6, M7]

## No JAR versus in-memory classes

**Exploded directory:** plausible using the same existing-Path-to-URL mechanism. This removes an archive, not a generated artifact. Keep the entire selected directory immutable while the process can read its classes/resources. It needs its own launch result. [F5, F6]

**Pure in-memory byte arrays:** not established. `getMixins` returns names; `MixinInfo.loadMixinClass` asks the active bytecode provider; Knot resolves a class resource URL and opens a stream. Merely defining a Class in a private loader does not expose the required bytes/resources to this provider. [F6, F7, M5, M6]

A reflected replacement resource loader, custom URL/filesystem machinery or replacement Mixin service would be a separate invasive research direction, not evidence that the present route supports memory-only classes. This report recommends a metadata-free cache artifact, not “pure in-memory mixins.”

## Safety, Windows and production limits

- **Without NekoJS:** removing NekoJS removes the only registered config/plugin. A stale cache artifact outside discovery paths should be inert; validate a real negative launch. Do not place the cache on the launcher's classpath independently or expose another automatically discovered config.
- **Fail closed before enumeration:** disabled/profile/side/namespace/hash/ABI/production gates must run before path admission and before getMixins returns names, not solely in shouldApplyMixin. Required errors must remain explicit rather than silently continuing with wrong hooks. [M2, M6]
- **Next launch:** generate outside callbacks; first preparation and declaration changes can require restart. A second hash cannot untransform targets already defined in this JVM. Keep bridge no-op/lease behavior before runtime creation and after root teardown.
- **Windows immutable selection:** the [implementation record](<../implementation/2026-11-07-mixinjs.md#L37-L45>) already describes a loaded-JAR replacement AccessDeniedException. That is repository evidence, not a new Fabric result. Write a new content-hash path, replace only a small selection pointer atomically, never replace/delete a path admitted to Knot in this process, and collect obsolete hashes only after shutdown. The directory alternative must not mutate selected files either.
- **Remapping:** classpath addition does not call runtime mod remapping. Candidate remapping occurs during mod load; Fabric's development refmap/remapper setup is not a complete bytecode/descriptor mapping pipeline for arbitrary new artifacts. Use exact runtime-namespace bytes/selectors for the narrow development experiment. General obfuscated production output, refmaps, hashes and cross-node mapping remain separate acceptance work. Preserve the current production gate. [F2, F4, F5]
- **Access/class tweakers:** cached metadata is not newly admitted as Fabric class-tweaker metadata. Continue rejecting compiler operations that require unavailable access or solve that independently. [F1, F4]

## Falsifiable minimal real-launch experiment — proposed only

Use an isolated Windows instance with the actual packaged NekoJS fixture, Java 25, Loader 0.19.3 and selected Mixin 0.17.3+mixin.0.8.7, initially dedicated server. Do not rely solely on Loom's development classpath.

1. Embed a tiny plugin/static config and prebuild one metadata-free immutable cached artifact: one string-targeted mixin, one helper outside the mixin package, a small plan resource and a deterministic injected marker. No guest compiler or runtime root loads from the plugin.
2. Target a fixture preLaunch implementation class that is the controlled fixture's first post-unlock target load. Its target method should have a deterministic observable result. Record ordered markers: phase, plugin constructor/onLoad, path admission, getMixins, target application, preLaunch body, ordinary NekoJS initialization. Never preload the target from the plugin. This tests the class initiating selection, not merely a late target.
3. Record Knot target-loader identities, actual resource/code-source origins and successful provider bytecode access without defining the mixin class. Assert no early target, Graal or root initialization.
4. Require changed target result, an injection marker plus transformed-bytecode export/audit, successful helper linkage and an unchanged Fabric mod-ID set. Server startup alone is insufficient. Any missing requirement falsifies the complete candidate contract.
5. Repeat with an immutable directory to test “no JAR” separately. Neither result proves memory-only admission.
6. Negative launches: absent NekoJS with stale cache; disabled; wrong hash/ABI/side/namespace/Minecraft/Loader identity; production mode; corrupt/missing artifact; duplicate classes; deliberately preloaded target. Require no wrong injection/linkage, or explicit fail-closed startup error where appropriate. Specifically verify rejected selections produce no getMixins names.
7. Select hash B on restart while retaining hash A physically. Require only B and no replacement/deletion of the loaded old artifact. Repeat on the second node and client before cross-node/client claims.

A bounded JVM-only iterator/resource probe could reduce uncertainty but would not prove native bootstrap order or first-target transformation. No such probe was implemented this turn.

## Exact remaining gaps and decision boundary

1. Packaged Fabric launch proof of onLoad classpath admission and transformation of the initiating target is missing.
2. Real startup combinations may preload targets or trigger reentrant plugin/helper linkage; selected Mixin replacements also need detection.
3. Bootstrap-owned admission receipts are not connected to the current root-owned plan path.
4. Client/server, callback ABI, teardown, disabling, corrupted cache, duplicate names and Windows lifecycle acceptance remain incomplete.
5. Production remapping and extra class-tweaker support remain unsolved; existing production restrictions stay.
6. Directory feasibility has no launch proof; memory-only admission has no established mechanism.
7. No API compatibility claim beyond the pinned Loader/Mixin versions. Detect unsupported versions and fail closed rather than falling back silently to late preLaunch registration.

**Decision:** challenge “Fabric requires a separate carrier MOD” as an architectural certainty. Prefer embedded config/plugin + internal immutable cached code source + getMixins for the next experiment; do not claim execution before DEFAULT, supported public API, or completed implementation.
