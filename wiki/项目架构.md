# 项目架构

> 本页面向**给 NekoJS 贡献代码、写插件 mod、或想理解内部实现**的开发者。脚本作者不需要读。

## 总览

NekoJS 是一个基于 **GraalVM/GraalJS** 的多平台 Minecraft 脚本引擎。

```text
                  ┌─────────────────────────────────────────┐
                  │            脚本（JS/TS/JSX）             │
                  └────────────────────┬────────────────────┘
                                       │ GraalJS Polyglot Context
                  ┌────────────────────▼────────────────────┐
                  │           NekoJS 运行时                  │
                  │  ┌──────────────────────────────────┐   │
                  │  │ core/  编译前端 / 模块 / 沙盒      │   │
                  │  │ script/ 脚本生命周期 / reload     │   │
                  │  │ api/   公开 API / 扩展点          │   │
                  │  │ probe/ 类型声明生成               │   │
                  │  │ plugin/ 插件 bootstrap            │   │
                  │  └──────────────────────────────────┘   │
                  └────────────────────┬────────────────────┘
                                       │ 平台抽象 SPI（IPlatform）
                  ┌────────────────────▼────────────────────┐
                  │           平台实现                       │
                  │      NeoForge 26.x / 1.21.1 / Fabric     │
                  └─────────────────────────────────────────┘
```

## 模块结构

引擎层是两个普通 Gradle 子项目（对外契约类型与引擎实现同住 `common`，靠包划分 + lint 边界），MC 相关代码住在一棵由 stonecutter 管理的版本共享树里。

```text
NekoJS/
├── common-api-processor/    # 注解处理器：编译期检查 spec 覆盖
├── common/                  # 跨平台引擎，不依赖 MC；产物整体内嵌进各平台 fat jar
│   └── src/main/java/com/tkisor/nekojs/
│       ├── api/             #   对外契约包：插件接口、适配器、事件、catalog
│       │                    #   零 MC/加载器/Graal import（guardLint L1 强制，ADR-0007）
│       ├── core/            #   运行时心脏：Graal Context、编译器、模块、Node shim
│       ├── script/          #   脚本生命周期：ScriptManager、reload、工作区
│       ├── probe/           #   类型声明生成
│       ├── eventbus/        #   事件总线实现
│       ├── bindings/        #   与 MC 无关的绑定类
│       └── platform/        #   平台抽象 SPI
├── buildSrc/                # 节点构建约定：nekojs.neoforge-node / nekojs.fabric-node
├── src/                     # 版本共享树，四个节点共用这一份
│   ├── main/java/           #   版本差异用 //? if >=26 守卫和 replacements 表达
│   │                        #   加载器差异用 //? if neoforge / //? if fabric 整文件守卫
│   ├── main/resources*/     #   AT / mixins / interface injection（26.x 与 1.21.1 分层）
│   └── test/java/           #   共享测试
├── versions/                # 每节点的参数（gradle.properties）+ 该节点专属源码
│   ├── 1.21.1/  26.1.2/  26.2.0/     # NeoForge 节点
│   ├── 26.1.2-fabric/                # Fabric 26.1.2 节点
│   └── 26.2.0-fabric/                # Fabric 26.2.0 节点（当前复用 source bridge）
└── settings.gradle.kts      # stonecutter 版本图 + 两个引擎子项目
```

节点专属源码有两种用途：一是各版本的 compat 实现（`platform/compat/` 下的门面实现），二是两个时代差异大到不便用守卫表达的孪生文件——共享树放 26.x 主干，`versions/1.21.1/src/` 放同名的 1.21.1 实现，stonecutter 按节点选用其中一份。

详见 [构建系统](构建系统)。

## 三个核心子系统

### 1. 运行时（`core/`）

GraalJS Polyglot `Context` 的装配与生命周期：

- **`NekoSharedEngine`**：进程级单例 Graal `Engine`，所有 Context 共享。
- **`NekoCoreContext`**：不可变 record，打包 engine + sandboxConfig + classFilter + errorTracker。
- **`NekoSandboxFactory`**：ContextBuilder，每 ScriptType 构建一个 Context。设 `HostAccess`、`ClassFilter`、IO（jail 到游戏目录）、JS 选项（`js.ecmascript-version=latest`、`js.commonjs-require=true` 等）。
- **`NekoSharedHostAccess`**：构建 `HostAccess`，把所有 `JSTypeAdapter` 注册为 `targetTypeMapping`。
- **`ClassFilter`**：`Predicate<String>`，高危 Java 类黑名单（Runtime/Process/ClassLoader/反射/io/nio/net/polyglot 本身等）。

### 2. 编译前端与模块系统（`core/compiler/`、`core/module/`）

- **TypeScript**：`NekoTypeScriptCompiler` 是手写的 lexer 基础**可擦除 TS**前端，擦除类型注解、`type`/`interface`、泛型、`as`/`satisfies`，把 `enum`/`namespace` 转 IIFE。
- **JSX**：`NekoJsxCompiler` 把 JSX lowering 到 `__nekoJsxFactory` 调用（classic runtime）。
- **ESM**：`core/module/esm/` 是完整的 native ESM 实现，自带 lexer/parser/linker，状态依次为 NEW、LINKING、LINKED、EVALUATING、EVALUATED，支持热重载（`ModuleReloadCoordinator`）。
- **Node shim**：`core/node/` 提供 fs/path/buffer/process/timers/util/events/assert/os/test 的 Java+JS 实现。
- **`java:` 模块**：`NekoModuleResolver` 把 `java:package/path` 解析为合成 ESM 模块。

### 3. 插件与扩展点（`api/`、`core/plugin/`）

NekoJS 的扩展模型是**插件即 API**：

- **`NekoJSPlugin`**（`api/NekoJSPlugin.java`）：~20 个 default 钩子方法的接口。内置功能（`NekoJSCorePlugin`）和第三方插件实现同一接口。
- **`@RegisterNekoJSPlugin`**：标记插件类，各加载器的 loader（`NeoForgePluginLoader` / `FabricPluginLoader`）扫描发现。
- **`NekoJSBasePluginManager`**：发现、过滤（`clientOnly`/`requiredMods`）、实例化、按 priority 排序。
- **`NekoPluginBootstrap`**：编排所有扩展点（`nekojs:bindings`、`nekojs:adapters`、`nekojs:events`、`nekojs:recipe_schemas` 等），收集后冻结注册表，发布 `NekoPluginRuntime`。
- **`NekoPluginExtensionPoint`/`NekoPluginExtensionProvider`**：开放式 SPI，插件可注册自定义扩展点。

详见 [插件开发](插件开发)。

## 平台抽象（SPI）

不是 Java ServiceLoader，而是**手动单例 init**：

| SPI | 位置 | 作用 |
|---|---|---|
| `IPlatform` + `Platform` 门面 | `common/.../platform/` | 环境信息（`isClient`/`getMcVersion`/`capabilities`/`defaultScanPackages()`，后者给 probe 包过滤用）。平台启动时 `Platform.init(new NeoForgePlatform())` 一次。 |
| `NekoIdCompat` | `common/.../platform/` | 在 `NekoId` 与平台原生 ID（`Identifier` / `ResourceLocation`）之间转换。 |
| `NekoCatalogPlatformProvider` | `common/.../api/catalog/` | 给 probe 喂注册表字面量、recipe namespace handler、host extension 声明。每个平台各实现一个。 |
| `@RegisterNekoJSPlugin` 发现 | 各加载器的 loader | 扫描注解类，交给 common 的 plugin manager。 |

平台能力由 `PlatformCapability` 枚举表达，共 10 个特性标志：`TAGS`、`RESOURCE_PACKS`、`CLIENT_SCREENS`、`CLIENT_KEYBINDS`、`CLIENT_RENDERERS`、`RECIPE_HOT_RELOAD`、`RECIPE_SCHEMA_AWARE`、`NETWORK_CUSTOM_CHANNEL`、`NBT_BINARY_IO`、`RECIPE_VIEWER`。

要注意它的定位：**这是给脚本做 feature detection 用的信息面**——脚本读 `Platform.get().capabilities()` 判断某个特性能不能用，平台实现负责把声明写准。引擎内部的功能裁剪不看这些标志位，而是走 `IPlatform` 的默认方法（没实现的平台默认返回空或 null）。

spec 的平台范围是另一套机制，用 `@PlatformAvailability(Scope)` 声明：`ALL` / `NF_ONLY`（26.x 与 1.21.1）/ `NF26_ONLY`（只有 26.x）/ `CR_ONLY`。编译期由 `SpecCoverageProcessor` 按 `-Anekojs.platform=nf26|nf121|cr` 强制检查。

## 字节码注入机制

给原版类加行为的方式按版本不同：

| 平台 | 机制 |
|---|---|
| **NeoForge 26.x** | `interfaceInjectionData`（`nekojs.interface_injection.json`）+ 空的 `Mixin implements *Extension`。这是最干净的做法 |
| **NeoForge 1.21.1** | 只用 Mixin `implements`——这个版本上 interface injection 用不了 |

## 事件系统（`api/event/` + `eventbus/`）

- **`EventGroup`**：命名的事件总线集合，`group.server("name", EventClass)` 等工厂方法。
- **`EventBus`/`CancellableEventBus`/`DispatchEventBus`**：总线接口，dispatch 版支持按 key 分发（如按方块/物品 id）。
- **`EventBusJS`**：GraalJS 面向的 `ProxyExecutable`，让脚本能 `ServerEvents.recipes(cb)` 这样调。
- **`EventBusForgeBridge`**：把加载器自己的事件（NeoForge 的 `IEventBus`）桥接进中立总线。
- **`api/event/` 持接口，`eventbus/` 持实现**（`EventBusImpl`/`CancellableEventBusImpl`/`dispatch/*`）。

## 配方系统（`api/recipe/` + 平台 `wrapper/`、`bindings/recipe/`）

- **`RecipeTypeDefinition`**：schema 定义（namespace/type/fields/constructors/unique）。
- **`RecipeTypeDefinitionStorage`**：三层优先级合并（auto-discovered < plugin override < data-driven JSON）。
- **`RecipeSchemaAutoDiscovery` + 各版本的 `MinecraftRecipeSchemaScanner`**：反射 MC 的 `RecipeSerializer.codec()` 自动生成 schema。
- **`RecipeNamespaceProxy` / `SchemaRecipeBuilder` / `FallbackNamespaceProxy`**：脚本侧 `event.recipes.<ns>.<type>(...)` 的代理层。解析时依次尝试 handler 方法、schema，最后用原始 JSON 兜底。
- **`RecipeManagerMixin`**：缓存原始配方 JSON 并应用脚本配方。

## Probe（`probe/`）

`ProbeCoordinator` 跑共享 BFS 类收集（带配置缓存），把结果分发到注册的 `ProbeBackend`（`ProbeBackendRegistry` + `probe.toml` 的 `ProbeConfig`/`ProbeConfigLoader`）各自反射 Java 类渲染声明文件，落盘统一走 `ProbeOutputCommitter` 的就地逐文件同步；内置 TypeScript 与 Python 两个 backend。详见 [Probe 类型生成](Probe-类型生成)。

## 设计原则

1. **JSON 优先**：配方、数据尽量用 JSON，脚本只写逻辑。
2. **绑定即原版类**：能直接暴露 MC 类就暴露，少造 wrapper。
3. **避免 Graal `Value` 泄漏**：API 边界尽量用具体 Java 类型，`Value` 只在 interop 层用。
4. **引擎层不依赖 MC**：MC 相关代码只住版本树，不进 `common`（这条由构建期的 lint 强制）。
5. **插件即 API**：内置功能与第三方插件走同一扩展面。

## 还没做完的事

- 文档注解：`@Doc` / `@Param` / `@Return` / `@Overload` / `@DeprecatedNekojs` 已实现（会进 probe 生成的 `.d.ts`；重载签名还有一条适配器自动通道，见 [注解体系](注解体系)）；`@Example` / `@TypeOverride` / `@Since` 仍是设想（`@Since` 依赖还不存在的 API 版本线）。
- 编译器目录的可读性债：TS 类型擦除器（`NekoTypeScriptCompiler` 内的 `Eraser`，约 1.9k 行）与 `PythonEmitter`（约 2.5k 行，目录里最大）是两个手写源到源改写器，拆分收益纯可读性、无 API 影响。
- 公开 API 还没有 SemVer 冻结线。
