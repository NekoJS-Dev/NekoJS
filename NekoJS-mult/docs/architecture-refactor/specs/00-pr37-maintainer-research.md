# PR 37 维护体验回归约束规格

Status: ready-for-agent
Type: spec

## Problem Statement

PR 37 是一次未合并的通用注册表骨架尝试。它用较少的骨架类暴露了真正昂贵的维护成本：扩展点缺少完整生命周期，数据依赖被伪装成注册顺序，结果只能从静态可变全局读取，新增能力容易牵动上下文、bootstrap 和下游接线。作者为此付出了多处登记、同步和接线成本，最终留下的是实验骨架，而不是可交付实现。

当前实现中的 Point、Handle、`dependsOn`、freeze 和结果发布已经解决其中一部分问题。本次重构若把它们重新当作待实现功能，会重复设计并破坏现有收益；若在整理运行时、注册表和公开面时丢掉这些语义，则会让 PR 37 的维护体验回归。本规格因此把历史证据固定为回归约束：既不重造已修复部分，也不让已经明确的失败模式重新进入标准实现。

## Solution

以 PR 37 的调查结论作为维护者体验基线，保护当前 Point/Handle 模型已经建立的可观察契约，并把它纳入后续重构的验收。实现者应能证明：扩展点仍有完整生命周期和显式依赖，插件仍能通过句柄取得冻结后的结果，新增事件、Adapter、扩展点和版本仍可沿维护者入口追踪到 owner、事实源、依赖方向和测试。

历史 skeleton 只用于识别风险和建立回归断言，不作为目标接口。未由 00 闭合的模块归属、运行时生命周期、公开契约和验证门禁分别服从 01、04、05、07 等 Resolution。

## User Stories

1. 作为维护者，我希望 PR 37 的结论只作为历史维护体验回归约束，以便不把已经解决的 Point/Handle 问题重新当作新功能重造。
2. 作为维护者，我希望每个扩展点都有清晰的初始化、收集、完成、合并和结果发布阶段，以便能解释一次插件贡献何时、如何生效。
3. 作为维护者，我希望扩展点之间的数据依赖通过显式声明表达，以便不再依赖注册顺序或全局完成回调制造隐式时序。
4. 作为 Java 插件作者，我希望贡献完成后通过稳定句柄读取产物，以便不依赖初始化前可能为空的静态全局。
5. 作为 Java 插件作者，我希望完成后的扩展点产物不可变，并且每轮 bootstrap 独立初始化，以便 reload 和测试之间不会互相污染。
6. 作为 Java 插件作者，我希望内置扩展点与第三方扩展点走同一条贡献路径，以便作者只需理解一套模型。
7. 作为维护者，我希望作者便利门面始终是 Point 事实源的投影，并由机械配对约束守护，以便新增通道不会产生第二个事实源。
8. 作为维护者，我希望新增事件、Adapter、扩展点和版本时都能从入口追踪到 owner、事实源、依赖方向、受影响节点和测试，以便维护成本可被真实验收而不是靠目录整洁宣称改善。
9. 作为维护者，我希望注册元信息、对象类型工厂、脚本对象和 loader 时机保持职责分离，以便任何一项变化都不会迫使整条注册链路同步修改。
10. 作为 Java 插件作者，我希望冲突、环依赖、未知依赖和未完成依赖以明确错误失败，以便问题不会退化为静默漏注册或错误顺序。
11. 作为脚本作者，我希望 KubeJS 风格的统一注册入口和必要的底层 Java 逃逸能力继续可用，以便既有便利写法和高级用法都不会因内部整理而消失。
12. 作为维护者，我希望历史的 `onFinish` 补丁、静态可变结果表、无语义 Scope 和万能上下文扩张不会被当作标准接口，以便局部 workaround 不会重新固化。
13. 作为维护者，我希望维护体验由真实任务试做和现有契约测试共同验证，以便新结构确实降低登记、同步和追踪成本。
14. 作为维护者，我希望本规格明确区分历史证据、当前实现和后续裁决，以便不会把 PR 的建议误当成现行架构或新的实施授权。

## Implementation Decisions

- PR 37 作为历史证据基线使用，不作为目标架构或可直接照搬的实现。其文件规模、提交演进和骨架细节只用于建立回归断言。
- 当前 Point/Handle 模型是受保护基线：Point 拥有自包含生命周期，依赖显式声明并参与拓扑校验，结果经句柄取得，完成后冻结，bootstrap 轮次相互隔离。
- 已由当前模型解决的扩展点生命周期、依赖顺序和结果访问不得重新打开为“新功能”；后续重构只能在不回归这些契约的前提下调整归属和实现。
- 作者便利门面是 Point 的投影，Point 是收集语义的事实源；配对测试继续机械约束两者关系，不冻结私有类分布。
- 每个扩展点必须能说明其初始器、收集器、完成器、合并策略、错误语义和结果所有权；缺失任一项时不得以“已有接口”为由宣称可交接。
- 依赖必须通过显式声明和拓扑排序表达。环依赖、未知依赖和未完成的数据依赖必须 fail-fast，注册顺序只能作为同层稳定 tie-breaker。
- 结果在完成后不可变，每轮 bootstrap 重新初始化；旧轮次句柄不得静默读取新轮次状态。
- 不把 PR 37 的 `onFinish` 全局副作用、静态可变全局、无语义 Scope、静默反射跳过或万能上下文扩张重新引入标准接口。
- 新增事件、Adapter、扩展点和版本四项维护任务作为回归验收：维护者必须能从入口定位 owner、事实源、依赖方向、受影响节点和测试。
- 本票不重新裁定模块归属、运行时所有权、公开签名、loader 时序或迁移策略；这些由后续已闭合票的 Resolution 决定。

## Testing Decisions

- 测试的最高 Seam 是 Java 插件贡献面与 `NekoJSPlugin`/Point/Handle 的可观察契约，不测试 bootstrap 私有循环或类分布。
- `PluginHookPairingTest` 是配对 prior art。成功断言是每个作者门面钩子都有唯一 Point、每个内置点都在配对表内；失败断言是遗漏、重复或未配对 `register*` 钩子立即变红。
- `NekoPluginBootstrapV2Test` 是依赖与产物 prior art。成功断言是显式依赖会重排执行并通过句柄取得已完成结果；失败断言是环依赖、未知依赖和未声明数据依赖都在约定阶段 fail-fast 且错误可定位。
- `NekoPluginExtensionPointTest` 与 `NekoPluginExtensionProviderTest` 是生命周期和冻结窗口 prior art。成功断言是完成产物稳定、注册窗口按约定关闭；失败断言是完成后仍可修改、跨轮状态泄漏或旧句柄读取新状态。
- `DeepFreezeTest` 用于保护冻结后不可见后续注册的可观察行为；测试不应依赖结果对象的内部身份或具体容器实现。
- 维护者四类任务试做是外部行为验收，不是新增测试框架。每次试做都要记录入口、owner、事实源、依赖方向、受影响节点和测试；需要多处猜测或静默同步时视为失败。
- 现有测试未覆盖真实外部 addon discovery、fat jar 依赖和完整 reload 链路，这是已记录缺口。获准实施后应在现有 JUnit 和 loader smoke 资产上补足，不另造全仓测试框架。

## Out of Scope

- 重做已经解决的 Point/Handle 生命周期、依赖或结果句柄功能。
- 照搬 PR 37 的 NeoForge 26.2 skeleton、Item-only builder 或具体注册表内容实现。
- 在本规格中重新裁定模块归属、单一运行时 owner、公开 API、Stonecutter、语言管线或迁移策略。
- 建立 GitHub issue、标签镜像或新的测试框架。
