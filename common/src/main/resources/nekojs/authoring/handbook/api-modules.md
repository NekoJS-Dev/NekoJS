# Stable and version API modules

Use the declarations generated by the current instance and Script Type. Stability does not imply availability in every loader, Minecraft version or Script Type.

```ts
import { ID, Native } from "nekojs/api/stable";
import { Item } from "nekojs/api/version";

const resource = ID.resource("minecraft:stone");
const nativeId = Native.ids.toNative(resource);
const restored = Native.ids.fromNative(nativeId);
```

The stable module exposes `ID`, the explicit `Native` interoperability bridge, and SERVER-only `ServerEvents.tickPre` / `tickPost`. `I18n` is CLIENT-only. The version module exposes the current node's `Item` helper and published event groups. Query the actual module and member signatures before using them; Fabric and NeoForge event sets differ. Plugin exports use `nekojs/api/stable/<modid>` or `nekojs/api/version/<modid>`.

ESM named imports and CommonJS destructuring use the same frozen, Context-local namespace:

```ts
const { ID } = require("nekojs/api/stable");
const id = ID.of("stone"); // nekojs:stone, preserving the legacy default
```

Literal `require` routes are typed; an unknown string route returns `unknown`. A module-only export creates no global. Existing global bindings and event groups remain supported; existing domain modules such as `nekojs/commands` are separate and unchanged. Importing a member unavailable in the selected environment fails instead of producing a placeholder.

## ID and native values

`ID.of` retains the historical permissive, nonblank namespace/path grammar. `ID.resource` is strict: namespace `[a-z0-9_.-]+`, path `[a-z0-9/._-]+`, default namespace `nekojs`; it does not trim, lowercase or repair input. Native ID conversion also validates this strict grammar. Invalid IDs produce `NEKO-4056`.

`Native.ids` converts in both directions using the selected node's actual native identifier class. Native bridge parameters and returns are intentionally profile-specific, not portable wrappers. This bridge does not fabricate loader objects or make arbitrary native APIs stable.

## Plugin publication

In the existing binding hook, publish a public view explicitly:

```java
registry.register(Binding.of("Widget", helper, WidgetView.class), expose -> expose.stable());
```

Use `versioned()` for native-dependent helpers. The configured overload is module-only; call the legacy overload separately only when a global is also intended. The loader supplies the owning mod ID. A missing owner, duplicate export, invalid export name, empty target or repeated target fails with `NEKO-4057`. Public view types constrain both the runtime members and generated declarations; implementation-only overloads are not exposed. Ordinary publication does not require a managed contract or hand-written manifest.

Declare event publications beside their source definition. The callback configures independent targets of one source bus:

```java
var group = EventGroup.of("MachineEvents");
var changed = group.server("changed", ChangedEvent.class, api -> {
    api.versioned();
    api.stable(ChangedView.class, event -> new ChangedView(event.getCount()))
            .scriptTypes(ScriptType.SERVER);
});
// In the plugin event hook:
registry.register(group);
```

The per-event declaration supplies the stable allowlist automatically. `stable()` without a converter publishes the original payload only if it passes portable public-type validation. The builder is frozen when the definition callback returns. `group.expose(api -> api.versioned())` declares a group-wide version publication; group-wide stable declarations still require explicit `events(...)`. Do not also select the same category for an event already covered by a group-wide declaration.

`registry.register(group)` installs the legacy group and consumes its publication declarations with the current plugin owner. Defining or reading a static GROUP never registers it globally. Disjoint declarations with the same owner, category and group name merge into one module export, preserving each event's scope and original bus; duplicate event publications fail. When source groups merge, a group-wide version selection stays limited to that contributor's source events.

The configured `registry.register(group, expose -> expose.stable().events("changed").view("changed", ChangedView.class, converter))` overload remains a module-only extension for sources defined elsewhere; it publishes only the supplied configuration. A projection of a cancellable event is rejected until a control mapping is provided. Optional `scriptTypes(ScriptType.SERVER)` restricts each publication to exact script types, intersected with source visibility; it never widens a bus or changes legacy global scope. Both targets share the source bus and listener lifecycle.

## Release observations

Probe emits `@special/api-modules.json` from the same module registrations. It records the profile, Script Type, category, callable signatures, Bean access and event payload surface. Release tooling can read it with `ApiModuleBaseline.fromJson` and compare an older observation using `old.compareTo(next)`. Stable removals and contractions fail compatibility; version API changes and precise native bridge signature changes are reported separately. These generated observations are author promises, not verified managed contracts or proof of cross-version runtime acceptance.

## Events and current boundaries

Module event subscriptions use the same bus, priority/order and generation lifecycle as their legacy publication. Stable event publication requires an explicit event allowlist; a projected public payload exposes only its declared members. Projection does not silently provide native cancellation controls.

### Stable server ticks

Available in SERVER scripts on both NeoForge and Fabric:

```ts
import { ServerEvents } from "nekojs/api/stable";

ServerEvents.tickPre(event => {
  if (event.tick % 20 === 0) console.info("Server tick", event.tick);
});
ServerEvents.tickPost(event => {
  console.info("Completed tick", event.tick);
});
```

The immutable `StableServerTickEvent` payload has one read-only Bean property, `tick`. It snapshots the event server's native `getTickCount()` value; there is no script-owned clock or zero-based rebasing. Supported nodes increment the native count before pre, so the first ordinary tick is 1 and pre/post for the same tick see the same native count. Script reloads do not alter the server count. New-server initialization and integer overflow follow Minecraft rather than an additional counter. Callbacks run synchronously on the server owner thread, use normal event priority/order, and are not cancellable. Retaining the view retains only its numeric snapshot, not a server/native handle. The view exposes no `server` or native cancellation methods. There is no native unwrap for this snapshot.

For native payload members, import `ServerEvents` from `nekojs/api/version` (use a local alias when also importing the stable group). Legacy global `ServerEvents` still receives the original node payload; other lifecycle events remain version-only.

Stable `NativeEvents` and `Native.unwrap` remain unpublished. NativeEvents needs thread-gate and candidate rollback/per-script cleanup guarantees. Unwrapping needs an audited, callback-scoped native-backed view; plain JavaScript objects are not native handles.
